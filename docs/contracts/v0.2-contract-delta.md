# V0.2 contract delta and compatibility matrix

**Status:** active contract-delta record for the `0.2` schema line.
**Scope:** what the V0.2 rebase changed, what it only reserves, and what it deliberately
left alone.

## What this document is, and is not

This file records the disposition of each contract seam at the `0.1` → `0.2` boundary.

It is **not** a source of truth that any code reads, and it is not a second SSOT
competing with the models. The canonical statements live in
`src/agent_foundry/models/` and are enforced by tests; this file explains them and
records the decisions that are *not* expressed as code, precisely so that a later slice
does not have to rediscover them.

**Documentation is not execution evidence.** Nothing here claims any runtime behavior.
A row marked *planned* is a decision about scope, not a report of work done, and must
not be read as partial implementation. Absence of a row is not permission either: a
seam this document does not name has no recorded disposition, which is `UNKNOWN`.

## 1. Contract seam disposition

| Seam | Disposition in 0.2 | Where it stands |
|---|---|---|
| `WorkClass` wire format | **changed in 0.2** | Values moved from `SCREAMING_SNAKE` to lowercase kebab (`ADOPTION` → `adoption`). Member names are unchanged, so symbolic call sites are unaffected. Migration and the fail-closed rule are implemented in `src/agent_foundry/models/compat.py` and hooked into `VersionedContract`. |
| `ProjectProfile` — first-class descriptive contract | **planned, not implemented here** | Introduced by M1 work. No model, no synthesis logic, and no field on any existing contract exists in this slice. |
| `OutcomeContract` | **planned, not implemented here** | M3. No model exists. `OutcomeCapability` in `work.py` is the current, narrower descriptive type and is not a substitute for it. |
| `ExecutionRun` / `WorkspaceLease` / `WriteLease` identity | **reserved, unchanged** | `ExecutionRunRef`, `WorkspaceLeaseRef` and `WriteLeaseRef` in `models/work.py` remain reserved extension points carrying identity fields only. They stay reserved for the whole of V0.2. Real execution identity — a run that actually ran, a lease that was actually held — is V0.3, because it requires an execution runtime that does not exist. |
| `OperatingModel` / `DecisionRights` profiles | **planned, not implemented here** | M2. No model exists. |
| Controlled Apply / execution runtime / MCP facade | **out of the V0.2 line entirely** | V0.3. `docs/foundry/09-release-and-versioning.md` §3 previously predicted these for `v0.2.x`; that prediction is withdrawn there. |
| `foundry_compat` default range on `CapabilityRegistry` / `ToolkitLock` | **changed in 0.2** | `">=0.1,<0.2"` → `">=0.2,<0.3"`. Forced: the range is evaluated against the running package version, so a `0.2.0.dev0` build could not load the registry it ships. The floor moved as well as the ceiling because a `0.1` runtime provably *cannot* read a `schema_version: "0.2"` artifact — it refuses it with `SchemaCompatibilityError ... minor newer than supported` — so `">=0.1,…"` would have been an envelope asserting something false. See §4 for why this is a *narrowing*, not a widening. |

## 2. Deferred vocabulary inconsistencies — recorded, not changed

Two vocabularies are also inconsistent with the lowercase-kebab convention that
`WorkClass` was just brought into line with. They are **not changed in this slice**.
They are recorded here so a later slice finds a decision rather than a discovery.

| Vocabulary | Current values | Inconsistency | Disposition |
|---|---|---|---|
| `MessageType` | `REQUEST`, `DELEGATION`, `HANDOFF`, `EVIDENCE`, `DECISION`, `REJECTION`, `BLOCKER`, `ESCALATION`, `STATE_UPDATE` | `SCREAMING_SNAKE` | **deferred.** Not changed in 0.2. Changing it is a further breaking wire change and belongs in its own versioned slice, with its own migration entry. |
| `ReviewOutcome` | `approved`, `rejected`, `changes_requested` | `changes_requested` is snake, not kebab | **deferred.** Not changed in 0.2. The other two members are already conformant, so a change touches exactly one token. |

Other vocabularies also serialize `SCREAMING_SNAKE`: `AdoptionAction`, `EvidenceState`,
`ValidationOutcome`, `FindingDisposition`. They are observably a different kind of
value — verdicts and attained states rather than descriptive classifications — and this
slice did not examine whether that distinction was intended, so it makes no claim either
way and changes nothing. They are named here so their absence from the deferred table
above is a recorded gap rather than an oversight.

## 3. Serialized-artifact compatibility matrix

Every V0.1 separately-persisted contract class, and what happens when a real `0.1` file
of that class is handed to a `0.2` build. Three dispositions only:

- **loads unchanged** — no token in the artifact changed; the declared
  `schema_version` is raised to `0.2` on load, because a loaded artifact is a
  current-version artifact.
- **loads via migration** — a changed token is rewritten to its canonical spelling on
  load, and the declared `schema_version` is raised to `0.2`.
- **fails closed** — the artifact declares `0.2` or newer while carrying a `0.1`
  token, which is a contradiction rather than an old file.

| Contract class | Carries a changed token? | `0.1` artifact | `0.2` artifact with a legacy token |
|---|---|---|---|
| `WorkItemContract` | yes — `work_class` | loads via migration | fails closed (`ContractMigrationError`) |
| `WorkPlan` | yes — nested `WorkItemContract`s | loads via migration | fails closed when the nested `WorkItemContract` itself declares `0.2` |
| `SkillSpec` | yes — `triggers.work_classes` (list) | loads via migration | fails closed (`ContractMigrationError`) |
| `CapabilityRegistry` | yes — via its nested `SkillSpec`s | loads via migration **if** its own `foundry_compat` admits the running version (see the row below) | fails closed when the nested `SkillSpec` itself declares `0.2` |
| `ProjectManifest` | no | loads unchanged | n/a |
| `AdoptionPlan` / `AdoptionChangeSet` | no | loads unchanged | n/a |
| `TaskToolkit` | no | loads unchanged | n/a |
| `ToolkitLock` | no changed token, but carries `foundry_compat` | **fails closed** (`UnmigratableContractError`) when the declared `foundry_compat` excludes the running version — which the stock v0.1 value `">=0.1,<0.2"` does. Loads via migration when the declared range admits it. | n/a |
| `CapabilityRegistry` (its own `foundry_compat`) | as above | same rule: a v0.1 registry declaring `">=0.1,<0.2"` fails closed | n/a |
| `ExecutionBundle` | no typed `work_class` field; the class can appear inside free-form provenance prose | loads unchanged | n/a |
| `EvidenceBundle` / `ExecutionReceipt` | no | loads unchanged | n/a |
| `CapabilitySpec` / `WorkflowSpec` / `RoleContract` | no | loads unchanged | n/a |
| `IntegrationSpec` | no declared `WorkClass` field, but `adapter_options` is a `FreeFormMapping` that may contain *any* key, including `work_class` | loads unchanged; free-form values are returned verbatim | n/a — a colliding key in free-form data is provider-owned and is never a migration input (see below) |
| `ProjectIntake` / `ToolConnectorSpec` / `ValidatorSpec` | no | loads unchanged | n/a |

### Registered but currently unreachable

`AdoptionGap.suggested_work_class` and `CapabilityUnit.work_class` are in the migration
registry, and **that registration currently buys nothing.** Both types are only ever
nested inside `DecompositionInput`, which is a plain `FoundryModel` with no
`schema_version`, so the before-validator never runs over them. A legacy
`SCREAMING_SNAKE` token at either site produces a generic pydantic enum error, not a
migration and not a `ContractMigrationError`.

They are registered anyway so that if either container later becomes a versioned
contract, migration is already correct rather than newly missing. Making them reachable
today would mean versioning a decomposition *input*, which is a contract decision this
slice did not take and does not pre-empt.

This is stated rather than glossed because the earlier wording — "migrate wherever they
appear inside a versioned contract" — was vacuously true and read as coverage.

### Free-form data is out of scope, by type

The traversal is **type-directed**: it follows the contract's declared `model_fields`
annotations, not key names in the payload. A value is rewritten only where the
enclosing model declares that field as `WorkClass`-typed.

Where a declaration is ambiguous the walker **refuses rather than guesses**. Two shapes
are refused, both raising `MigrationPlanError` the first time the model is planned:

- a field naming **two different nested models** (`A | B`, or `dict[A, B]`), which has
  no single declared type to descend against — following one would rewrite data the
  other owns, reintroducing the free-form defect behind a union;
- a field with **more than one arm that reaches a model** (`list[Model] | Model`, the
  one-or-many idiom), where following either arm migrates some payloads and silently
  skips others depending on which arm was written first.

`Model | None` — the shape every union-typed field in the repository actually has — is
unaffected: `None` reaches no model, so there is exactly one reaching arm.

Refusal is chosen over handling deliberately. A silent gap here is under-migration: a
legacy token that is neither rewritten nor failed closed, degrading to a generic enum
error that reads like a typo. `MigrationPlanError` can only fire on a defect in this
repository's own model definitions, deterministically at plan time, and a reflection
test plans every shipped model, so it cannot reach a consumer.

Plan and descent share **one** classifier (`_descent_route`) rather than each deriving
"is this descendable?" from the traversal's branch structure. That duplication is what
allowed a field to be registered as a child and then never walked, so it was removed
rather than kept in sync.

This matters most at `IntegrationSpec.adapter_options`, a `FreeFormMapping` that is an
adapter-owned namespace. A key-name match at arbitrary depth would rewrite a provider's
option value on a v0.1 artifact, and reject a perfectly valid v0.2 one — an unversioned
compatibility break riding along with the versioned one, and Core reaching into
provider-specific data, which is what provider-neutrality exists to prevent.

The same traversal supplies the nested-contract boundary, by type rather than by
sniffing for a `schema_version` key: a field whose declared type is itself a
`VersionedContract` is not descended into.

Implementation and guard share one definition of "registered field": the walker builds
its per-model plan from the same annotations the exhaustiveness test reflects over.
They disagreed once — the guard scoped by declared type while the walker scoped by key
name — and the result was a green suite over a broken behaviour.

### `foundry_compat` is refused, never rewritten

`foundry_compat` is an owner-declared **normative** compatibility assertion, not a
derived value. Migration does not touch it.

Bumping `schema_version` 0.1 → 0.2 while leaving `foundry_compat: ">=0.1,<0.2"` in place
would produce an artifact declaring schema 0.2 and pinning a range that excludes 0.2 —
self-contradictory, and it would surface much later during toolkit resolution as a
complaint about the range rather than about the artifact being an unmigrated v0.1 file.
Silently broadening the range instead would widen a compatibility authority on the
strength of an inference, which this repository forbids.

So migration fails closed at load with `UnmigratableContractError`, naming the contract
class, the field, the declared range, the running package version, the version pair it
was migrating between, and the fact that no migration is provided for the field. The
fields refused this way are listed in `UNMIGRATABLE_DECLARED_FIELDS` in
`models/compat.py`; today that is `foundry_compat` alone.

### Where the rule is enforced

`VersionedContract` runs the migration as a `model_validator(mode="before")`, so it
applies on every entry path — `model_validate`, and therefore `load_yaml`, `load_json`,
and anything built on them. There is no loader that can bypass it.

A nested mapping that declares its own `schema_version` is a separately versioned
contract and is skipped by the outer walk: it gets this same validator when pydantic
descends into it, and so migrates against *its own* declared version. A `0.2` work plan
carrying `0.1` work items is therefore migrated correctly rather than rejected.

An artifact whose declared `schema_version` is already incompatible on MAJOR/MINOR
grounds is handed through untouched, so the version incompatibility is the error
reported. Naming the token instead would name the smaller of two facts.

## 3a. Recorded residuals

Neither of these is fixed here. They are recorded so the disposition exists.

**A migrated artifact is indistinguishable from a native one.** Migration raises
`schema_version` and leaves no trace that it occurred. Downstream — in evidence,
receipts, and reconciliation — a v0.1 artifact that was migrated on load looks exactly
like one authored against 0.2. Nothing reads a "was migrated" fact because nothing
records one. Against this repository's evidence norms that is a real gap: it means the
provenance of a contract's tokens is not recoverable after load. Building a provenance
mechanism is **not** in this slice's scope and was not attempted; this is a recorded
disposition, not a plan.

**A migrated artifact may retain a `foundry_compat` floor that is now false.** Migration
refuses to rewrite an owner declaration (see §3), and refuses outright when the declared
range excludes the running version. But a range such as `">=0.1,<0.3"` *admits* the
running version, so the artifact migrates — and the result declares `schema_version:
"0.2"` while still asserting that a `0.1` runtime may use it. By the same argument that
moved the default floor to `">=0.2,…"`, that assertion is false: a `0.1` runtime cannot
read a `0.2` artifact. The behaviour is deliberate and unchanged — refusing to rewrite
an owner declaration is the correct rule, and inferring a new floor would be exactly the
widening §4 forbids — but the owner is left holding a range that no longer says
something true, and nothing warns them.

## 4. What did not change

- No authority axis widened. No autonomy, external-effect, reversibility, or
  credential boundary moved.
- The one compatibility-envelope change, `foundry_compat` `">=0.1,<0.2"` →
  `">=0.2,<0.3"`, is a **narrowing on the floor** and a move of the ceiling: it admits
  strictly fewer runtimes below and does not claim any runtime that cannot read a `0.2`
  artifact. It is recorded as a seam in §1 rather than buried in the changelog, because
  a compatibility range is an authority-shaped declaration even when it moves inward.
  Migration itself never edits this field — it refuses (see §3).
- No new contract class was added. `compat.py` adds two error types
  (`ContractMigrationError`, `UnmigratableContractError`) and one migration function to
  the public surface, all recorded in `tests/fixtures/models_public_exports.json`.
- The V0.1 release record is **preserved**, which is not the same as byte-identical.
  `docs/release-notes/v0.1.0.md`, `docs/foundry/v0.1-release-certification.md` and the
  `v0.1.0` CHANGELOG entry are untouched. `docs/foundry/v0.1-readiness-report.md`
  carries one **appended, dated resolution note** under §5.13, and no rewritten text:
  the original finding, which said the `WorkClass` break was deferred to a versioned
  change, stands exactly as written. Those documents describe what V0.1 actually did,
  at the schema version it did it at, and remain accurate as history.
