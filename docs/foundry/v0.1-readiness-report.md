# V0.1 Readiness Report

Work Item: SUE-302 (AF8) — prove the V0.1 vertical slice, then freeze the boundary.
Measured at `main` + AF8. The suite was 1269 tests at `2b87b52`; it is 1376 here.

This report is written to one rule: **a stage that exits without raising has proved
nothing.** Every number below comes from an artifact that was produced and examined,
not from a command that returned zero. Where a measurement is a judgement, it says so
and names the evidence it was judged from.

---

## 1. Verdict

**The V0.1 slice is proven end to end, for a project whose owner has declared its
characteristics. It was not proven before this Work Item, and it does not hold for a
project that has not declared them.**

Three findings decide that verdict, and all three were found by running the path
rather than by reading it:

1. **An owner declaration was read and then discarded.** `.foundry/project.yaml`
   carries the full `ProjectManifest` shape. Inspection read exactly one key from it
   (`intake_mode`) and reported the rest as "not observable from repository inventory
   alone" — including `project.name`, which was sitting in the file. Adoption then
   emitted `KEEP foundry-project-declaration — "Existing declaration is authoritative
   and compatible"` in the same run in which it ignored 13 of its 14 values.

2. **The consequence was total.** With an all-unknown manifest, toolkit resolution
   selects nothing: zero capabilities, zero skills, zero roles. `compile_work_item`
   then raises `CompileError` for every role in the registry. **The path
   `repository -> ExecutionBundle` could not be completed for any repository**,
   including this project's own designed brownfield fixture.

3. **Two further breaks sat behind that one**, invisible until it was fixed: the only
   work class the adoption planner emits (`ADOPTION`) was excluded from every
   write-bearing skill in the builtin registry, and the adoption gap model carried no
   repository path, so an adoption Work Item compiled to repository-write authority
   over an **empty write scope** — a bundle that passes every structural check and
   authorizes nothing.

Point 3 is the failure mode the completion gate names. It is now caught by validation
rather than passed: `execution-bundle-completeness` rejects a repository-write bundle
that grants no write path.

### What is proven

* Repository -> intake -> manifest -> adoption change set -> causal Work Item ->
  Project Toolkit + lock -> integration preflight -> Task Toolkit -> ExecutionBundle
  -> Markdown -> validation -> evidence -> receipt -> reconciliation, over a
  controlled fixture **and** over this repository, producing artifacts that were
  examined field by field.
* The compiled bundle authorizes a change it could actually make: a non-empty write
  scope over files that exist, inside both the Work Item scope and the role bound.
* Validation rejects all four required failure classes, with substantive findings
  (19 broken-fixture tests; see §6).
* The run is deterministic across `PYTHONHASHSEED` and across four working
  directories, proved by digesting every serialized artifact in child processes.
* The full path over this repository leaves it byte-identical — size, mode and mtime
  compared for every path.

### What is not proven

* **Nothing executed anything.** V0.1 compiles and verifies contracts. The evidence
  bundle in every run is what a runtime *would* report; the receipt records that
  substitution as a limitation. "The bundle is coherent" is not "the work was done".
* **No inference supplies a manifest characteristic.** Across 12 local repositories,
  the median manifest is 1 of 14 fields populated (§4). A project that has not
  declared still cannot reach an ExecutionBundle. That is now *reported* — adoption
  proposes `MIGRATE foundry-project-declaration` — rather than silently produced.
* **The default registry does not fit a project it was not shaped for** (§5.7).
* **Validation's own limits are those in `verify/claims.py`**, unchanged by this Work
  Item except where noted in §6.4. In particular `receipt-completeness` is still not
  an independent derivation, and complete in-process producer isolation remains a
  known residual (SUE-350).

## 2. What AF8 changed, and why each change was necessary

Every change below was made because the slice could not be completed without it, and
each is generic: no project-specific rule was added to core.

| Change | Why it was unavoidable |
|---|---|
| Read every declared dimension from `.foundry/project.yaml` into `ClassificationFinding`s (`inspect/classification.py`) | Without it the manifest carries one field and the toolkit is empty. The eligibility machinery for `DECLARED` provenance already existed; only the reader was missing. |
| Promote declared values into every `ProjectManifest` field, including `project.name` and `assurance.required` (`adopt/manifest.py`) | Six fields were hardcoded `None`/`[]` at the synthesis site regardless of input. |
| Propose `MIGRATE foundry-project-declaration` for a brownfield project with no declaration (`adopt/changes.py`) | `MIGRATE` had no brownfield emit site, so a retrofit plan never told an owner to do the one thing that unblocks the rest of the pipeline. |
| Add `WorkClass.ADOPTION` to the `bounded-change`, `deterministic-test` and `independent-review` skill triggers (`toolkit/builtin_registry.py`) | The planner emits only `ADOPTION` items, and that class could select no skill but read-only inspection. Adoption work writes files — the planner marks its own changes `bounded-policy` for exactly that reason. |
| Select a Task Toolkit workflow only when its required skills are available (`toolkit/resolve.py`) | The fallback returned `sorted(available)[0]`, pinning a workflow the preference order had rejected and whose skills the item could not carry. AF7's `toolkit-coherence` validator rejected the result. |
| Add `AdoptionGap.scope`, and use typed `EvidenceClass` values in `_gap_to_unit` (`models/work.py`, `work/decompose.py`) | The gap carried a logical target name, not a path, so write authority intersected to nothing; and `required_evidence` was the prose `"implementation diff"`/`"validation output"`, which no evidence class names, so an adoption item's evidence was permanently unsatisfiable. |
| Compute forbidden scopes by containment (`compile/authority.py`) | A role bound of `tests/` narrowed to `tests/conftest.py` was emitted as forbidden *and* granted — a contradiction the containment validator correctly rejected. Only reachable with a file-level Work Item scope, which no unit test had. |
| Skip a virtual environment by its `pyvenv.cfg` marker, not by directory name (`inspect/traversal.py`) | `.venv-lane` is not `.venv`. It sorts before every source directory and holds thousands of files, so it consumed the entire 2000-entry budget and inspection reported "No test entrypoints observed" about this repository. |
| Reject a repository-write bundle with no write path (`verify/validators.py`) | The completion gate's own failure mode. Everything else about such a bundle is consistent. |
| Say how many selection records the rendered summary omitted (`render/markdown.py`) | The summary stopped at ten silently, so a truncated list read as the complete one. |
| Add `agent-foundry validate` (`cli.py`, `verify/cli_api.py`) | AF7 shipped validation API-only. The facade holds no rule; `tests/e2e/test_e2e_cli.py` checks that structurally. |

Two of these — the workflow fallback and the forbidden-scope contradiction — were
**caught by AF7's validators during this run**. That is the validation layer doing the
job it was built for, on real producer output, and it is the strongest single piece of
evidence in this report that validation is not decorative.

## 5. Gap register

Classification: **project-local bug** | **reusable Foundry defect** | **missing
capability** | **deferred post-V0.1 feature**.
Against `docs/foundry/08`: **fix-now** | **bounded follow-up** | **intentional non-goal**.

Gaps marked *fixed in AF8* are recorded because they are what the slice found, not
because they remain open.

### 5.1 Declared manifest dimensions were discarded — *fixed in AF8*
**Reusable Foundry defect · fix-now.** Inspection read one key of the declaration;
synthesis hardcoded six fields to `None`/`[]`. Against `08` §4.1 (Profile Synthesis)
and `02` §6 ("classification **and approved declarations**"). The doc was right; the
code was incomplete.

### 5.2 `repository_revision` is unknown in a git worktree
**Reusable Foundry defect · bounded follow-up.** `git_head_revision` requires `.git` to
be a directory inside the root. A `git worktree` checkout has a `.git` *file* pointing
at a gitdir outside it, and containment refuses to follow — correctly. The cost is that
every downstream identity (evidence `proves_revision`, receipt `candidate_revision`,
reconciliation identity findings) has nothing to bind to. **Not fixed here**: following
the pointer means reading outside the repository root, which is a boundary decision, not
a bug fix. Options are a bounded read of the referenced gitdir under an explicit
allowance, or accepting the revision as a caller-supplied input. Pinned by
`test_repository_revision_is_unknown_in_a_git_worktree`.

### 5.3 Inspection has no notion of a nested project boundary
**Reusable Foundry defect · bounded follow-up.** A repository that contains other
repositories as test fixtures reports their `Dockerfile`s, `env.example`s and
`pyproject.toml`s as its own. Measured cost on this repository: 2 of 8 readiness
findings wrong, 15 of 17 adoption evidence refs pointing at fixtures. Any project with
`examples/`, `templates/`, or vendored sample apps has the same problem. A nested
`pyproject.toml`/`package.json`/`.git` is a strong, cheap boundary signal and nothing
consults it.

### 5.4 Readiness asserts absence without knowing the walk was truncated
**Reusable Foundry defect · fix-now.** `assess_readiness` receives observations and
conventions but not `TraversalStats`, so it cannot distinguish "no test entrypoints"
from "the walk stopped before `tests/`". Before §2's virtualenv fix this repository
produced exactly that false negative. 3 of 12 scanned repositories still reach the
2000-entry limit, so the false negative is live for them. **Not fixed here** — it
requires threading traversal stats into the readiness signature.

### 5.5 The 64 KB read limit silently excludes the largest files
**Reusable Foundry defect · bounded follow-up.** 351 files across 12 repositories
exceed it, including this package's largest module. The skip is *recorded* as a
`file-read-skipped` observation, which is the honest half; the missing half is that
nothing downstream treats "the biggest file was not read" as a limit on what
inspection may conclude.

### 5.6 Convention discovery knows four hardcoded patterns
**Missing capability · bounded follow-up.** Against `08` §4.3, which asks for
repository conventions, architectural boundaries, testing patterns, naming patterns and
existing agent-rule surfaces. What exists: a pytest mention, a commit-constraint
mention, a Makefile `test` recipe, a CI checkout step. Across 12 repositories only
three distinct subjects were ever produced, none above confidence 0.5, and the
strongest available fact — the declared runner in `pyproject.toml` — is never read.

### 5.7 The builtin `builder` role hardcodes a project shape
**Reusable Foundry defect · fix-now.** `write_scope=["src/", "tests/"]` in
`build_default_registry()`. Compiled write authority is the intersection of that with
the Work Item scope, so any change to `AGENTS.md`, `Makefile`, `.github/` or
`.foundry/` — which is most of what adoption touches — compiles to **no write
authority**. `08` §4.5 names this shape of thing explicitly: prefer predicates over
project-type branching. `CapabilityRegistry` is a supported input to every entry point,
so a consumer *can* override it; nothing derives it, and nothing tells them they need
to. **Not fixed here**: deriving a role write scope from the manifest is a design
decision, and hardcoding a wider default would be a different project-shape assumption.
The end-to-end tests supply the override the way a consumer would, and say so.

### 5.8 Nothing maps an `AdoptionChangeSet` onto `DecompositionInput`
**Missing capability · bounded follow-up.** `AdoptionGap` exists and
`decompose_work` consumes it; no published function produces one from a planned change.
`tests/e2e/pipeline.py` supplies the mapping in ~40 lines, stated in the open rather
than smuggled into `agent_foundry`, because *which* changes become work is a policy
choice a consumer may reasonably make differently. The seam is the one place the
advertised path `adoption plan -> causal Work Item` is not wired.

### 5.9 The Tier B entropy rule fires on ordinary explanation text
**Reusable Foundry defect · bounded follow-up.** 59 Tier B `high-entropy` findings
across six serialized artifacts from one run, every one on prose a human wrote to
explain a decision (`decisions[*].project_fact`, `provenance[*].project_fact`,
`limitations[*].reason`), and one on the entire rendered Markdown read as a single
string. **Tier A — the tier that actually gates — produced zero findings**, so nothing
leaked and the SUE-318 boundary held. The cost is a consumer running the scanner over
its own artifacts and seeing 59 non-secrets. Measured and pinned rather than left as an
unexamined "clean".

### 5.10 Task Toolkit does not narrow relative to Project Toolkit
**Missing capability · bounded follow-up.** Against `08` §4.6 (relevance selection and
progressive disclosure). For both measured targets the Task Toolkit is the Project
Toolkit exactly. Narrowing happens one stage later, at the role seam in
`compute_compiled_authority`. The rendered contract lists 4 skills of which the
compiled role may exercise 2.

### 5.11 `AdoptionAction.WRAP` has no emit site
**Missing capability · bounded follow-up.** Stated in §4. The vocabulary is one member
wider than the planner.

### 5.12 `AdoptionAction.BLOCK` is unexercised by real input
**Deferred post-V0.1 feature · bounded follow-up.** Two emit sites, zero occurrences
across 12 repositories, because `assess_readiness` never sets `blocker=True` for any
observable condition. The blocked-adoption path is covered by unit tests and by no real
repository.

### 5.13 `WorkClass` uses `UPPER_SNAKE` values while every sibling vocabulary is `kebab-case`
**Reusable Foundry defect · bounded follow-up.** A hand-authored Work Item YAML with
`work_class: adoption` is rejected; it must be `ADOPTION`. Every other enum in
`models/common.py` serializes lowercase. Cosmetic until someone hand-writes a contract,
which is exactly what the CLI's `--work-item` flag invites. Changing it is a contract
break and belongs to a versioned change, not to AF8.

### 5.14 README advertises five CLI commands that do not exist
**Project-local bug · fix-now.** `profile`, `work plan`, `render`, `reconcile` have no
subcommand; `resolve` and `adopt --preview` are spelled differently from what ships.
`validate` was in the same list and is added by this Work Item. The README is corrected
here to separate what ships from what is intended, rather than leaving a hedged
"approximately" to carry five absent commands.

### 5.15 `compile` emits a useless bundle that only `validate` rejects
**Reusable Foundry defect · bounded follow-up.** `compile_work_item` runs
`validate_execution_bundle_authority` but not the completeness validator, so the CLI
`compile` command happily prints a repository-write bundle with no write scope, and
only a separate `agent-foundry validate` call catches it. Pinned by
`test_compile_render_matches_the_committed_example`, which asserts the CLI output has
no `## Write scope` section where the committed example does.

## 6. Validation: what it caught, and what it still cannot

### 6.1 Two producer defects caught during this run
`toolkit-coherence` rejected the Task Toolkit produced by the resolver's own workflow
fallback. `write-scope-containment` rejected the authority block produced by the
compiler's own forbidden-scope computation. Neither was reachable from any existing
unit test; both required a real repository with a file-level Work Item scope.

### 6.2 One new rejection added
`execution-bundle-completeness` now rejects a bundle whose compiled authority is
`repository-write` and whose write scope is empty. Its claim in `verify/claims.py` is
updated in both directions: it now proves the bundle grants at least one write path,
and it now states that it cannot prove the path is the *right* one.

### 6.3 The four required failure classes
19 broken-fixture tests, each breaking exactly one property of an otherwise-accepted
pipeline output, with a control asserting the unbroken case passes first.

| Class | Break | Rejected by | Finding |
|---|---|---|---|
| policy violation | authority raised to `publication` | `authority-ceiling` | 4 BLOCKED — exceeds manifest, work item, permission profile, role |
| policy violation | write path `../outside-the-repository` | `write-scope-containment` | BLOCKED — does not resolve to a usable repository-relative bound |
| role separation | two roles over the same path in one run | `role-separation` | BLOCKED — overlapping write scope |
| role separation | reviewer names itself as implementer | `role-separation` | BLOCKED (and the model refuses to construct it) |
| role separation | review-only role holding write authority | `role-separation` | BLOCKED |
| missing evidence | no items | `required-evidence` | 2 MISSING, one per required class |
| missing evidence | untyped `kind` only | `required-evidence` | MISSING — unrecognised is not proven |
| missing evidence | failing result | `required-evidence` | rejected |
| missing evidence | no revision named | `required-evidence` | rejected |
| missing evidence | class both attained and exempt | `evidence-bundle-completeness` | rejected |
| unhealthy integration | required but unobserved | `integration-preflight` | MISSING — "unobserved is not healthy" |
| unhealthy integration | observed `unavailable` | `integration-preflight` | 2 BLOCKED |
| unhealthy integration | required but undeclared | `integration-preflight` | BLOCKED |
| unhealthy integration | auth-implying health, no auth block | `integration-preflight` | BLOCKED |

Every rejection above carries at least one rejecting finding with a specific message.
An empty report is not an acceptance: `ValidationReport.accepted()` is `False` for one.

### 6.4 What validation did *not* establish here
Per `verify/claims.py`, unchanged by this Work Item:

* `receipt-completeness` is **not** an independent derivation. It binds a receipt to
  the artifact handed in for comparison, and both sides wrap the same serializer.
* `toolkit-coherence` cannot prove the selected subset is the *minimum* one — which is
  exactly why §5.10's over-selection passed validation.
* `required-evidence` reads the evidence record; it does not re-run the test.
* `role-separation` separates contracts, not judgement.
* Complete in-process producer isolation remains a residual (SUE-350); a process
  boundary is the complete answer and is out of scope for V0.1.

Validation accepting this slice means the contracts are coherent and bounded. It does
not mean the work described was done, or done well.

## 7. Core APIs, CLI, and the MCP question

`08` §3.7 asks whether a future MCP facade would need a separate path. Confirmed by
inspection, as instructed, and no facade was built:

* Every stage is a function over contracts returning contracts. No entry point
  performs I/O beyond reading the target repository, and none holds an adapter handle.
* `cli.py` imports only published package entry points (`agent_foundry.inspect`,
  `.adopt`, `.toolkit`, `.compile`, `.render`, `.verify`) — checked structurally by
  `test_the_cli_reaches_the_same_functions_the_python_api_does`.
* `verify/cli_api.py`, added here, is dispatch only. A test parses its AST and fails if
  it defines any `validate_*` function of its own, so a second implementation behind a
  second surface cannot appear quietly.
* The one place the CLI and the Python API differ is inputs, not logic: the CLI cannot
  express a project-supplied `CapabilityRegistry`, so `agent-foundry compile` over a
  project like this one uses the builtin builder write scope and produces a bundle with
  no write scope (§5.15). That is a CLI surface gap, not duplicated logic.

A third surface would call the same functions. Nothing about the current shape blocks
it.
