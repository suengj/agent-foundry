# V0.1 Readiness Report

Work Item: SUE-302 (AF8) — prove the V0.1 vertical slice, then freeze the boundary.
Measured at `main` + AF8. The suite was 1269 tests at `2b87b52`; it is 1434 here.
Every figure below was re-measured after the last change that could move it.

This report is written to one rule: **a stage that exits without raising has proved
nothing.** Every number below comes from an artifact that was produced and examined,
not from a command that returned zero. Where a measurement is a judgement, it says so
and names the evidence it was judged from.

---

## 1. Verdict

**The V0.1 slice is proven end to end, for a project whose owner has declared its
characteristics. It was not proven before this Work Item, and it does not hold for a
project that has not declared them.**

Three findings from the first pass decided that, and all three were found by running
the path rather than by reading it:

1. **An owner declaration was read and then discarded.** `.foundry/project.yaml`
   carries the full `ProjectManifest` shape. Inspection read exactly one key from it
   (`intake_mode`) and reported the rest as "not observable from repository inventory
   alone" — including `project.name`, which was sitting in the file. Adoption then
   emitted `KEEP foundry-project-declaration — "Existing declaration is authoritative
   and compatible"` in the same run in which it ignored 15 of its 16 values.

2. **The consequence was total.** With an all-unknown manifest, toolkit resolution
   selects nothing: zero capabilities, zero skills, zero roles. `compile_work_item`
   then raises `CompileError` for every role in the registry. **The path
   `repository -> ExecutionBundle` could not be completed for any repository**,
   including this project's own designed brownfield fixture.

3. **Two further breaks sat behind that one**, invisible until it was fixed: the only
   work class the adoption planner emits (`ADOPTION`) was excluded from every
   write-bearing skill in the builtin registry, and the adoption gap model carried no
   repository path, so an adoption Work Item compiled to repository-write authority
   over an **empty write scope** — a bundle that passes every structural check and
   authorizes nothing.

### What independent review then found, and what it corrected

The first pass was reviewed and returned REQUEST_CHANGES with five blockers. Four were
product defects this report had classified too leniently, and one was the completion
gate firing on the harness itself. All five are fixed, and the corrections are the more
important half of this Work Item:

* **The end-to-end verdict did not consult most of its own validators.**
  `PipelineResult.accepted()` aggregated four artifact checks. A run carrying an
  unhealthy required integration reported `accepted() == True` while
  `validate_integration_preflight` rejected the same inputs on its own. The
  broken-fixture tests proved *individual validator* behaviour and were described in
  this report as proving pipeline output. They did not. There is now a published
  `agent_foundry.verify.validate_compiled_slice` that runs all fourteen validators and
  records anything it could not run; `SliceValidation.accepted()` is False whenever a
  validator did not run; and the four failure classes are proved by mutating the
  pipeline's **input** and asserting the verdict flips.

* **The Task Toolkit was not the minimum subset.** It equalled the Project Toolkit
  exactly on every measured input. `docs/foundry/04` §4 specifies subtraction, and
  least capability is a safety property, so this was a product failure and not the
  bounded follow-up it was filed as. Selection is now need-based, and the reduction is
  measured in §3.

* **A hardcoded project shape produced a default false success.** The builtin `builder`
  role declared `write_scope=["src/", "tests/"]`, so `agent-foundry compile` succeeded
  with repository-write authority and an empty write scope for any project shaped
  differently — and only a separate `validate` call would catch it. The bound now comes
  from the project's own declaration, compilation refuses rather than emitting, and the
  end-to-end harness no longer supplies a registry override.

* **`WRAP` had no producer.** Stating the absence honestly was not sufficient while
  `docs/foundry/02` §7 lists it as a brownfield category: code and contract disagreed.
  It now has an emit site (§4).

* **A durable architecture document carried volatile work status.** Removed.

### What a second review round then found

Three items, all of which this report had got wrong about itself:

* **A test's name still claimed a property its body did not assert.** The first round
  fixed the aggregation underneath
  `test_the_broken_integration_reaches_the_pipeline_as_a_rejection` and left the test
  itself unchanged — so the substantive defect was fixed while the test named for it
  still proved nothing. Fixed, and every test under `tests/e2e/` whose name states a
  property was re-read against its body; seven were corrected (§5.17).
* **A gap was reclassified to fix-now and left unfixed.** §5.3, the nested-project
  boundary, on this report's own evidence — a compiled write scope over seven files
  belonging to fixture repositories. A readiness report that files something as
  fix-now and does not fix it is contradicting itself. Fixed, with a mutation test
  that plants a complete second project inside a target and requires the target's
  diagnosis to be unchanged.
* **The opening test count was stale.** Every figure in this report has been
  re-measured after the last change that could move it, and the ones the boundary fix
  moved are stated as before-and-after rather than silently replaced.

### What is proven

* Repository -> intake -> manifest -> adoption change set -> causal Work Item ->
  Project Toolkit + lock -> integration preflight -> Task Toolkit -> ExecutionBundle
  -> Markdown -> validation -> evidence -> receipt -> reconciliation, over a
  controlled fixture **and** over this repository, producing artifacts that were
  examined field by field.
* The end-to-end verdict runs **all 14 published validators**, records nothing as
  un-run, and is False if any of them could not run. Coverage is asserted before the
  verdict is read, in every test that reads it.
* All four required failure classes flip that verdict when injected at the pipeline's
  input, not merely when a validator is called directly (§6).
* The compiled bundle authorizes a change it could actually make: a non-empty write
  scope over files that exist, inside the Work Item scope, the project's declared
  envelope, and the role bound.
* The Task Toolkit is a strict subset of the Project Toolkit, and every subtraction
  names its reason.
* The run is deterministic across `PYTHONHASHSEED` and across four working
  directories, proved by digesting every serialized artifact in child processes.
* The full path over this repository leaves it byte-identical — size, mode and mtime
  compared for every path.
* No registry override, and no other project shape, is supplied by the harness.

### What is not proven

* **Nothing executed anything.** V0.1 compiles and verifies contracts. The evidence
  bundle in every run is what a runtime *would* report; the receipt records that
  substitution as a limitation. "The bundle is coherent" is not "the work was done".
* **No inference supplies a manifest characteristic.** Across 12 local repositories,
  the median manifest is 1 of 16 fields populated (§4). A project that has not
  declared still cannot reach an ExecutionBundle. That is now *reported* — adoption
  proposes `MIGRATE foundry-project-declaration` — rather than silently produced.
* **`agent-foundry validate` alone cannot give the slice verdict.** Six of the fourteen
  validators need inputs no single artifact carries. The command reports what it could
  not run and exits 3 rather than 0 when anything applicable was skipped.
* **`AdoptionAction.BLOCK` is unexercised by real input** (§5.12).
* **Validation's own limits are those in `verify/claims.py`**, unchanged except where
  §6.2 notes. `receipt-completeness` is still not an independent derivation, and
  complete in-process producer isolation remains a known residual (SUE-350).
* **The 12-repository aggregate figures are not reproducible from this branch** — the
  targets are not in it. The *method* is: `tests/e2e/friction_survey.py` is committed
  and tested (§4, §9).

## 5. Gap register

Classification: **project-local bug** | **reusable Foundry defect** | **missing
capability** | **deferred post-V0.1 feature**.
Against `docs/foundry/08`: **fix-now** | **bounded follow-up** | **intentional non-goal**.

Gaps marked *fixed* are recorded because they are what the slice found, not because
they remain open. Where independent review rejected a classification, the correction is
stated with it.

### 5.1 Declared manifest dimensions were discarded — *fixed*
**Reusable Foundry defect · fix-now.** Inspection read one key of the declaration;
synthesis hardcoded six fields to `None`/`[]`. Against `08` §4.1 (Profile Synthesis)
and `02` §6 ("classification **and approved declarations**"). The doc was right; the
code was incomplete.

### 5.2 `repository_revision` is unknown in a git worktree
**Reusable Foundry defect · bounded follow-up.** `git_head_revision` requires `.git` to
be a directory inside the root. A `git worktree` checkout has a `.git` *file* pointing
at a gitdir outside it, and containment refuses to follow — correctly. The cost is that
every downstream identity (evidence `proves_revision`, receipt `candidate_revision`,
reconciliation identity findings) has nothing to bind to. **Not fixed here**: following
the pointer means reading outside the repository root, which is a boundary decision, not
a bug fix. Options are a bounded read of the referenced gitdir under an explicit
allowance, or accepting the revision as a caller-supplied input. Pinned by
`test_repository_revision_is_unknown_in_a_git_worktree`.

### 5.3 Inspection had no notion of a nested project boundary — *fixed*
**Reusable Foundry defect · fix-now.** A repository containing other repositories as
test fixtures reported their `Dockerfile`s, `env.example`s and `pyproject.toml`s as its
own. Measured on this repository before the fix: **2 of 8 readiness findings wrong, 22
of 25 adoption evidence references pointing into `tests/fixtures/projects/`, and a
`WRAP` Work Item whose compiled write scope was seven fixture `env.example` paths.**

That last one is why this was reclassified from bounded follow-up to fix-now, and why
it could not be left there. The bundle was a *correct compilation of a wrong
diagnosis*: every authority check passed, containment held, provenance was complete,
and the work it authorized was work nobody wanted done. No validator can catch it —
`write-scope-containment` proves a path lies inside its declared bounds, not that it is
the right path — so the only place to fix it is where the evidence is attributed.

A directory below the root carrying its own project manifest (`pyproject.toml`,
`package.json`, `Cargo.toml`, `go.mod`, `setup.py`) or its own `.git` is a nested
project. Its contents are not evidence about the target, and every collector,
classifier and convention scanner reads the owned subset. The marker set is
deliberately narrower than `PACKAGE_METADATA_FILES`: a lock file travels with a project,
it does not constitute one, and splitting a repository at every `requirements.txt`
would hide most of it from its own diagnosis.

The exclusion is recorded, not silent. Each boundary emits a `nested-project`
observation, because "not attributed" has to be distinguishable from "not there" — the
same confusion a truncated traversal produced when it reported a repository with a full
test suite as having none.

After: **0 of 8 readiness findings wrong, 0 of 3 evidence references from fixtures, and
no `WRAP` proposed for this repository.** `tests/e2e/test_e2e_project_boundary.py`
plants a complete second project inside a target — its own manifest, `Dockerfile`,
`env.example`, instruction surface and `Makefile` — and requires that every claim the
target makes about its own surfaces is byte-identical before and after. The one thing
that legitimately changes, that a new directory exists, is asserted separately rather
than excluded and left unexamined.

**Residual.** The rule is a heuristic about ownership, not a proof of it. A monorepo
whose packages each carry a manifest will have those packages excluded from the root's
diagnosis, which is right for a workspace of independent services and arguably wrong
for one cohesive project split into modules. The boundary is always recorded, so the
decision is visible and a consumer can see what was set aside; there is no way today
to override it.

### 5.4 Readiness asserts absence without knowing the walk was truncated
**Reusable Foundry defect · fix-now.** `assess_readiness` receives observations and
conventions but not `TraversalStats`, so it cannot distinguish "no test entrypoints"
from "the walk stopped before `tests/`". Before the virtualenv fix this repository
produced exactly that false negative. 3 of 12 scanned repositories still reach the
2000-entry limit, so the false negative is live for them. **Not fixed here** — it
requires threading traversal stats into the readiness signature.

### 5.5 The 64 KB read limit silently excludes the largest files
**Reusable Foundry defect · bounded follow-up.** 298 files across 12 repositories
exceed it, including this package's two largest modules. The skip is *recorded* as a
`file-read-skipped` observation, which is the honest half; the missing half is that
nothing downstream treats "the biggest file was not read" as a limit on what
inspection may conclude.

### 5.6 Convention discovery knows four hardcoded patterns
**Missing capability · bounded follow-up.** Against `08` §4.3, which asks for
repository conventions, architectural boundaries, testing patterns, naming patterns and
existing agent-rule surfaces. What exists: a pytest mention, a commit-constraint
mention, a Makefile `test` recipe, a CI checkout step. Across 12 repositories only
three distinct subjects were ever produced, none above confidence 0.5, and the
strongest available fact — the declared runner in `pyproject.toml` — is never read.

### 5.7 The builtin `builder` role hardcoded a project shape — *fixed*
**Reusable Foundry defect · fix-now.** `write_scope=["src/", "tests/"]` in
`build_default_registry()`. Compiled write authority is the intersection of the
declared bounds with the Work Item scope, so any change to `AGENTS.md`, `Makefile`,
`.github/` or `.foundry/` — most of what adoption touches — compiled to **no write
authority**, and `agent-foundry compile` reported success for it. `08` §4.5 names this
shape of thing explicitly: prefer predicates over project-type branching.

Filed in the first pass as fix-now-but-not-fixed, with the end-to-end harness supplying
a registry override "the way a consumer would". Review rejected that: the harness was
manually supplying the project shape the product could not derive, so it proved nothing
about the default. The bound is now `ProjectManifest.authority.write_scope`, read from
the owner's declaration; the builtin role declares none; compiled authority intersects
every declared bound; and with no bound declared, nothing is granted. The harness
supplies no registry, asserted by
`test_no_project_supplied_registry_is_needed_to_compile_this_repository`.

### 5.8 Nothing maps an `AdoptionChangeSet` onto `DecompositionInput`
**Missing capability · bounded follow-up.** `AdoptionGap` exists and
`decompose_work` consumes it; no published function produces one from a planned change.
`tests/e2e/pipeline.py` supplies the mapping in ~40 lines, stated in the open rather
than smuggled into `agent_foundry`, because *which* changes become work is a policy
choice a consumer may reasonably make differently. The seam is the one place the
advertised path `adoption plan -> causal Work Item` is not wired.

### 5.9 The Tier B entropy rule fires on ordinary explanation text
**Reusable Foundry defect · bounded follow-up.** Tier B `high-entropy` findings across
the serialized artifacts of one run, every one on prose a human wrote to explain a
decision (`decisions[*].project_fact`, `provenance[*].project_fact`,
`limitations[*].reason`), and one on the entire rendered Markdown read as a single
string. **Tier A — the tier that actually gates — produced zero findings**, so nothing
leaked and the SUE-318 boundary held. The cost is a consumer running the scanner over
its own artifacts and seeing findings that are not secrets. Measured and pinned rather
than left as an unexamined "clean".

### 5.10 Task Toolkit did not narrow relative to Project Toolkit — *fixed*
**Reusable Foundry defect · fix-now.** Against `08` §4.6 and `04` §4 ("the minimum
subset needed for one Work Item/run… the subtraction is enforced, not aspirational").
For both measured targets the Task Toolkit was the Project Toolkit exactly, while the
compiled bundle permitted 2 of 5 capabilities — so narrowing happened one stage later,
at the role seam, and the contract's own stage did nothing.

Filed in the first pass as a missing capability and a bounded follow-up. Review
rejected that: least capability is a P0 product invariant, and `toolkit-coherence`
expressly cannot prove minimum selection, so its PASS never made the claim true.
Selection is now need-based — a workflow that requires the skill, a project policy that
requires it, or a typed evidence class the Work Item requires — with a read baseline so
an item can always look at its own scope, and every subtraction carries its reason.
Measured reduction in §3.

### 5.11 `AdoptionAction.WRAP` had no emit site — *fixed*
**Missing capability · fix-now.** Filed in the first pass as a bounded follow-up on the
grounds that stating the absence plainly was enough. Review rejected that, correctly:
`docs/foundry/02` §7 lists WRAP as a brownfield category, so code and contract
disagreed, and that is a defect whichever one is wrong. Resolved by giving WRAP a
producer rather than removing it from the contract, because the contract's definition
describes a real and common brownfield situation — a credential or integration surface
the repository already has, with nothing declaring how an agent should reach it. §4
records where it now fires.

### 5.12 `AdoptionAction.BLOCK` is unexercised by real input
**Deferred post-V0.1 feature · bounded follow-up.** Two emit sites, zero occurrences
across 12 repositories, because `assess_readiness` never sets `blocker=True` for any
observable condition. The blocked-adoption path is covered by unit tests and by no real
repository. Retained as UNVERIFIED: the zero occurrence is not coverage, and broad
brownfield decision-class coverage should not be claimed until a real blocker-producing
target is tested.

### 5.13 `WorkClass` uses `UPPER_SNAKE` values while every sibling vocabulary is `kebab-case`
**Reusable Foundry defect · bounded follow-up.** A hand-authored Work Item YAML with
`work_class: adoption` is rejected; it must be `ADOPTION`. Every other enum in
`models/common.py` serializes lowercase. Cosmetic until someone hand-writes a contract,
which is exactly what the CLI's `--work-item` flag invites. Changing it is a contract
break and belongs to a versioned change, not to AF8.

### 5.14 README advertised five CLI commands that do not exist — *fixed*
**Project-local bug · fix-now.** `profile`, `work plan`, `render`, `reconcile` have no
subcommand; `resolve` and `adopt --preview` are spelled differently from what ships.
`validate` was in the same list and is added by this Work Item. The README now
separates what ships from what is intended.

### 5.15 `compile` emitted a useless bundle that only `validate` rejected — *fixed*
**Reusable Foundry defect · fix-now.** `compile_work_item` ran
`validate_execution_bundle_authority` but not the completeness check, so the CLI
`compile` command printed a repository-write bundle with no write scope and exited 0.
Filed in the first pass as a bounded follow-up; review rejected that as precisely the
false success the completion gate prohibits. Compilation now refuses, with a message
naming the Work Item scope and the declared bounds it failed to intersect.

### 5.16 The end-to-end verdict consulted 4 of 14 validators — *fixed*
**Reusable Foundry defect · fix-now.** Not a product defect but a defect in this Work
Item's own evidence, and the one the completion gate exists to catch. Corrected as
described in §1 and §2; the property that now prevents it is that
`SliceValidation.accepted()` is False whenever any applicable validator did not run,
and `validate_compiled_slice` raises if a validator in the published catalog is neither
run nor recorded as skipped.

### 5.17 A test's name claimed a property its body never asserted — *fixed*
**Project-local bug · fix-now.** `test_the_broken_integration_reaches_the_pipeline_as_a_rejection`
asserted the health record was degraded and then called `validate_integration_preflight`
directly. It never checked that the pipeline rejected anything, and it passed while
`run_pipeline(...).accepted()` returned True for that exact input — which is how §5.16
survived a full round of self-review. Fixing the aggregation underneath it did not fix
the test, and a test whose name claims coverage it does not provide reads as coverage in
every later audit.

The assertion is added, and every test under `tests/e2e/` whose name states a property
was re-read against its body. Seven were corrected: four had their bodies strengthened
to check what they claimed (convention evidence is now read back out of the file it
cites; context relevance now requires a recorded cause; an absolute path is now searched
for in the artifacts rather than inferred from equal digests; "every committed example"
and "every committed fixture" now enumerate from the source of truth rather than from a
hand-written list), and three were renamed to claim only what they check.

### 5.18 Declared authority axes were never matched to classification findings — *fixed*
**Reusable Foundry defect · fix-now.** `verify.explain.AUTHORITY_AXES` paired each

`ClassificationFinding.dimension` the inspector emits, so the declared baseline was
always empty and `assess_inferred_fact_tightening` reported **every correctly-declared

### 5.19 `agent-foundry validate` cannot give the slice verdict alone
**Missing capability · bounded follow-up.** Six of the fourteen validators need inputs

permission profile, the work plan. The command now reports what it could not run and
exits 3 rather than 0 when anything applicable was skipped, and its `--help` names

## 6. Validation: what it caught, and what it still cannot

### 6.1 Three producer defects caught during this run
`toolkit-coherence` rejected the Task Toolkit produced by the resolver's own workflow
fallback. `write-scope-containment` rejected the authority block produced by the
compiler's own forbidden-scope computation. `decision-explainability` surfaced the
authority-axis mismatch the moment a declaration could populate those axes. None was
reachable from any existing unit test; all three required a real repository run.

### 6.2 Two new rejections added
`execution-bundle-completeness` rejects a bundle whose compiled authority is
`repository-write` and whose write scope is empty. Its claim in `verify/claims.py` is
updated in both directions: it now proves the bundle grants at least one write path,
and it now states that it cannot prove the path is the *right* one. §5.3's `WRAP`
write scope over seven fixture `env.example` files is what that limitation looked like
in practice: a valid grant over the wrong files, which no validator could have caught
and which had to be fixed where the evidence is attributed.

`write-scope-containment` now checks every declared bound, names which one a path fell
outside, and reports MISSING when no authority declared any bound at all. Its claim is
updated to match.

### 6.3 The four required failure classes, whole-path
Each break is injected at the **pipeline's input**, the full path runs, and
`PipelineResult.accepted()` must be False. A control asserts first that the unbroken
run is accepted **and** that all 14 validators ran with nothing skipped — without that,
an acceptance could mean the check never happened.

| Class | Break, at the input | Rejected by |
|---|---|---|
| policy violation | the compiler's authority intersection is neutralized, then its structural guard too | `authority-ceiling`, 4 BLOCKED |
| policy violation | the producer's guard alone, left in place | `CompileAuthorityError` — the producer refuses, and no artifact is emitted |
| role separation | a project-supplied registry lets `reviewer` write, and it is compiled concurrently under the same run id | `role-separation`, overlapping write scope *and* review-only role holding write |
| missing evidence | the run produces no evidence at all | `required-evidence`, one MISSING per required class |
| missing evidence | the run produces one of two required classes | `required-evidence`, naming the class still short |
| unhealthy integration | observed health is `unavailable` | `integration-preflight` BLOCKED — the exact run the first pass reported as accepted |
| unhealthy integration | nothing observed at all | `integration-preflight` MISSING, "unobserved is not healthy" |

A seventh whole-path test covers the seam between two of these: an unhealthy
integration is correctly subtracted by resolution, the bundle then carries no trace of
the request, and the verdict must still object rather than reporting NOT_REQUIRED for
an integration the caller asked for and could not have.

### 6.4 The same four classes, per validator
19 further tests break exactly one property of an otherwise-accepted artifact, each
with its own control. These prove validator behaviour; §6.3 proves the path.

| Class | Break | Finding |
|---|---|---|
| policy violation | authority raised to `publication` | 4 BLOCKED — exceeds manifest, work item, permission profile, role |
| policy violation | write path `../outside-the-repository` | BLOCKED — does not resolve to a usable repository-relative bound |
| policy violation | a granted path outside the declared envelope | BLOCKED, naming the bound |
| role separation | two roles over the same path in one run | BLOCKED — overlapping write scope |
| role separation | reviewer names itself as implementer | BLOCKED (and the model refuses to construct it) |
| role separation | review-only role holding write authority | BLOCKED |
| missing evidence | no items | 2 MISSING, one per required class |
| missing evidence | untyped `kind` only | MISSING — unrecognised is not proven |
| missing evidence | failing result | rejected |
| missing evidence | no revision named | rejected |
| missing evidence | class both attained and exempt | rejected |
| unhealthy integration | required but unobserved | MISSING — "unobserved is not healthy" |
| unhealthy integration | observed `unavailable` | 2 BLOCKED |
| unhealthy integration | required but undeclared | BLOCKED |
| unhealthy integration | auth-implying health, no auth block | BLOCKED |

Every rejection carries at least one rejecting finding with a specific message. An
empty report is not an acceptance: `ValidationReport.accepted()` is `False` for one,
and `SliceValidation.accepted()` is `False` for a set with anything un-run.

### 6.5 Compilation refuses before validation has to
The Work Item whose adoption change has no located evidence cannot bound a write, so
compilation raises rather than emitting a bundle. `validate` catching it afterwards was
the first pass's answer and was the wrong one: a compile command that exits 0 for work
that cannot be done is a false success wherever the second command is not run.

### 6.6 What validation did *not* establish here
Per `verify/claims.py`, unchanged by this Work Item except as noted in §6.2:

* `receipt-completeness` is **not** an independent derivation. It binds a receipt to
  the artifact handed in for comparison, and both sides wrap the same serializer.
* `toolkit-coherence` cannot prove the selected subset is the *minimum* one — which is
  why §5.10's over-selection passed validation for as long as it did.
* `required-evidence` reads the evidence record; it does not re-run the test.
* `role-separation` separates contracts, not judgement.
* `write-scope-containment` proves a granted path lies inside every declared bound; it
  cannot prove the bound is the right bound, or that the path is the one the work
  needs. §5.3 records what that cost before the nested-project boundary landed, and it
  is the reason a diagnosis defect cannot be answered with a validator.
* Complete in-process producer isolation remains a residual (SUE-350); a process
  boundary is the complete answer and is out of scope for V0.1.

Validation accepting this slice means the contracts are coherent, bounded, and
completely checked. It does not mean the work described was done, or was worth doing.

## 7. Core APIs, CLI, and the MCP question

`08` §3.7 asks whether a future MCP facade would need a separate path. Confirmed by
inspection, as instructed, and no facade was built:

* Every stage is a function over contracts returning contracts. No entry point
  performs I/O beyond reading the target repository, and none holds an adapter handle.
* `cli.py` imports only published package entry points (`agent_foundry.inspect`,
  `.adopt`, `.toolkit`, `.compile`, `.render`, `.verify`) — checked structurally by
  `test_the_cli_reaches_the_same_functions_the_python_api_does`.
* `verify/cli_api.py` is dispatch only. A test parses its AST and fails if it defines
  any `validate_*` function of its own, so a second implementation behind a second
  surface cannot appear quietly. `verify/slice.py` holds the whole-slice verdict and is
  subject to the same rule — it imports every check and defines none.
* `validate_compiled_slice` is what a facade would call for a safety verdict, and it
  takes contracts and returns a contract like everything else.
* The CLI and the Python API differ in **inputs**, not logic: `agent-foundry validate`
  can be handed one artifact and a few of its neighbours, so six validators have
  nothing to run against. That is now reported (`not_run`, exit 3) rather than left to
  look like a pass (§5.19).

A third surface would call the same functions. Nothing about the current shape blocks
it.

## 9. Reproducing this

```bash
python -m pytest -q                          # 1434 tests
agent-foundry doctor                         # exit 0
python -m tests.e2e.generate_examples        # regenerate examples/e2e-synthetic/
python -m pytest tests/e2e -q                # the end-to-end suite alone
python -m tests.e2e.friction_survey DIR ...  # the aggregate method in §4, on your own targets
```

Every artifact in `examples/e2e-synthetic/` is regenerated and byte-compared by
`tests/e2e/test_e2e_examples.py`, so the examples cannot drift from the code that
produces them. `examples/e2e-synthetic/slice-validation.json` is the committed output
of `validate_compiled_slice`, and a test asserts it covers the whole validator catalog
with nothing un-run.
