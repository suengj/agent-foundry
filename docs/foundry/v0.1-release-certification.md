Work Item: AF9 — certify the first public `v0.1.0`, without tagging it.

Measured at `main` = `7fddbd0`. Every command below was run; every output below was
captured from that run and pasted, not summarised. Where a check is a judgement rather

**This document certifies a release candidate. It does not perform a release.** No tag

left at `0.1.0.dev0` in every commit except the final one (§12).

### One caveat, reported honestly

A *different* corruption — deleting a module rather than making a call fail — never
reaches the diagnostic at all:

```console
$ mv .../site-packages/agent_foundry/toolkit/builtin_registry.py /tmp/
$ agent-foundry doctor
Traceback (most recent call last):
  File ".../bin/agent-foundry", line 5, in <module>
    from agent_foundry.cli import main
  ...
ModuleNotFoundError: No module named 'agent_foundry.toolkit.builtin_registry'
exit=1
```

The exit code is still `1`, because that is Python's default for an uncaught exception,
so a caller scripting against the documented codes is not misled. But `cli.py` imports
the whole package at module level, so the `[FAIL] capability registry: unavailable:`
branch — the one written for exactly this case, and marked `pragma: no cover - only on
a broken install` — cannot be reached by a missing-module corruption. The user sees a
traceback where the design intends a diagnostic. **Not a release blocker** (exit code
and the fact of failure are both correct); reported in §10 as a robustness follow-up.

## 7. Schema and version compatibility freeze

Nineteen separately-persisted contracts carry `schema_version` — every
`VersionedContract` subclass exported from `agent_foundry.models`:

```text
AdoptionChangeSet  AdoptionPlan     CapabilityRegistry  CapabilitySpec  EvidenceBundle
ExecutionBundle    ExecutionReceipt IntegrationSpec     ProjectIntake   ProjectManifest
RoleContract       SkillSpec        TaskToolkit         ToolConnectorSpec
ToolkitLock        ValidatorSpec    WorkItemContract    WorkPlan        WorkflowSpec
```

Every one is at `"0.1"` in this release, and every committed example artifact carries
`schema_version: '0.1'`.

### What a consumer can rely on

| Surface | Frozen value | Rule |
|---|---|---|
| `FOUNDRY_SCHEMA_VERSION` | `"0.1"` | accepts the same MAJOR and a MINOR no newer than supported |
| `ToolkitLock.foundry_compat` | `">=0.1,<0.2"` | evaluated on MAJOR.MINOR only |
| `CapabilityRegistry.foundry_compat` | `">=0.1,<0.2"` | a registry outside the range raises `SchemaCompatibilityError` at resolve time |
| Package version | `0.1.0` | `0.1.z` backward-compatible; `0.2.0` may break contracts |

Concretely: a `0.1` build reads a `0.0` or `0.1` artifact and **rejects** a `0.2` or
`1.0` one with `SchemaCompatibilityError`, naming the contract and both versions. There
is no silent coercion and no implicit migration.

### The version bump is compatibility-neutral — proved, not assumed

`_parse_foundry_version` strips the `.dev` suffix and compatibility compares
`(major, minor)` only, so `0.1.0.dev0` and `0.1.0` are indistinguishable to every compat
check:

```console
$ python -c "...compat check across the bump..."
running __version__ : 0.1.0.dev0
parsed              : (0, 1, 0)
parsed('0.1.0')     : (0, 1, 0)
  >=0.1,<0.2   dev0=True     0.1.0=True
  >=0.1        dev0=True     0.1.0=True
  ==0.1        dev0=True     0.1.0=True
  >=0.2        dev0=False    0.1.0=False
```

The freeze commit in §12 therefore cannot change any resolution, validation, or
compatibility outcome. It changes three string literals and the CHANGELOG.

### What may change before 1.0

Named explicitly so it is not a surprise: contract shapes at `0.2`; `WorkClass`
serialization moving from `UPPER_SNAKE` to `kebab-case` to match every sibling
vocabulary (a deliberate contract break, deferred); the spelling of the five CLI
subcommands the README lists as not built; anything not exported from the documented
modules.

### 8.3 Internal tracker identifiers: decided, not deferred

`09` §4 asked for "no private project names or internal tracker identifiers in durable
public content." At `7fddbd0`, bare `SUE-` identifiers appeared in **8 tracked files**
(21 occurrences): `CHANGELOG.md` ×1, `docs/foundry/v0.1-readiness-report.md` ×4, and six
test files, mostly as section comments attributing a regression to the Work Item that
found it.

A first pass at this Work Item removed them from `CHANGELOG.md` only and reported the
rest as an open owner decision. That was the wrong shape of answer: it left the contract
saying one thing while shipped artifacts did another, which is the exact defect AF8
refused to accept for `WRAP`. The decision is made here, and `09` §4 is amended so that
code and contract agree.

**The rule as written could not be satisfied.** Twenty-one merged pull-request titles
carry these keys permanently. If "durable public content" includes PR objects — and `09`
§4's own GitHub-object section says it does — then the repository violated the rule
before this Work Item began and could not be brought into compliance by editing files.
An unsatisfiable rule is not a standard; it is something every future audit has to
quietly ignore.

**What the rule is actually protecting.** The leak that matters is tracker *content* and
tracker *addresses* — an issue description, a review URL, a workspace slug. That is what
lets a reader reach material never meant to be public, and §9 records a live instance of
it. A bare key reveals only that an item exists.

**The resolution, in two parts.**

*Complied with, in documentation.* Every tracker identifier is removed from the two
public reports. `docs/foundry/v0.1-readiness-report.md` had four; each is replaced by the
fact it stood for, so the text is now more useful to a reader who could never have opened
the issue — a sentence reading "the …-318 boundary held" now reads "the embedded-secret
boundary held", which says the same thing to a maintainer and something real to everyone
else. This document had four; three are gone, and the fourth is a verbatim `git log`
quotation left unedited on purpose (§3). `CHANGELOG.md`, `README.md` and the release
notes name none. One incidental use in a test *vector* — a synthetic credential-shaped
string in a parametrized vocabulary list, where the key carried no provenance at all —
was renamed.

*Carved out, in source.* `09` §4.1 now permits a bare tracker key as source-level
provenance — in comments, commit messages and PR metadata, never as a URL and never as
pasted content. The **15** remaining occurrences, across six test files, are all of that
kind: a section comment of the form `# --- <KEY>: fail-closed unknown capability ids ---`
answers *why does this test exist?*, which the code cannot answer on its own. This
project treats evidence that supports its own claim as a first-class property; severing a
regression test from the defect that produced it would remove exactly that, in exchange
for hiding a string that 21 merged pull-request titles already publish.

The distinguishing test, now written into `09` §4.1: a key that records **why a durable
artifact is the way it is** is provenance and may stay; a key used as an incidental label,
or as a stand-in for a fact the text could simply state, is a reference and goes.

| `AKIAIOSFODNN7EXAMPLE` | **Tier A** `aws-access-key` — blocks |
| `orders-service-AKIAIOSFODNN7EXAMPLE` | Tier B `high-entropy` only — **advisory, does not block** |
| `tracker-token-ghp_ABCDEF…` | Tier B only — advisory |
| `orders-tracker-sk-live-RAWSECRETVALUE12` | Tier B only — advisory |
| `xyzAKIAIOSFODNN7EXAMPLE` | **nothing** |
| `svc_AKIAIOSFODNN7EXAMPLE` | **nothing** |
| `risk-assessment-v2` | nothing (correct — not a secret) |

The cause is `_TOKEN_BOUNDARY = (?<![A-Za-z0-9_-])`: Tier A only matches at a token
boundary. A hyphen-joined suffix falls through to Tier B, and a glued or
underscore-joined one is detected by **neither tier**. `raise_on_embedded_secrets` raises
on Tier A findings only, so Tier B is confirmed advisory in code as well as in claim.

The README and release notes state this in that stronger form, including the
underscore/glued case the brief did not mention.

### 10.2 One limitation restated more precisely

`AdoptionAction.BLOCK` **is** emitted — by two of the eight committed fixtures. The
readiness report's claim is narrower and correct: it is unexercised by *real* input,
0 occurrences across 12 surveyed repositories, because readiness assessment never marks
an observable condition as a blocker. The public text says that, not "never emitted".

### 10.3 What independent review then found, and what it corrected

The first pass of this Work Item was reviewed and returned REQUEST_CHANGES. Both
findings were correct, and both were defects in this audit's *own artifacts* — which is
the failure mode a hygiene audit is most prone to and least able to see.

**This document leaked two personal filesystem paths.** §2's interpreter-provenance

artifact of an already-public repository — three sections above a table asserting **0**
personal filesystem paths in tracked files. The audit was true of everything except

added, and every file this Work Item touches re-swept for the whole class: absolute home

**The tracker-identifier decision was half-applied.** The first pass removed the keys
