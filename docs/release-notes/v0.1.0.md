# Agent Foundry v0.1.0 — Public Preview

> **Draft release note for an untagged release.** `v0.1.0` has been prepared and
> certified but **not tagged and not published**. No `v0.1.0` Git tag and no GitHub
> release exist; both require explicit authorization from the repository owner. Until
> then this file describes a release candidate, and the "you can install it" instructions
> below work only from a clone of `main`.

**Status: experimental public preview. Not a stable API, and nothing here executes work.**

Agent Foundry takes a new or existing repository as input, diagnoses how that project
actually operates, prescribes an AI-native operating model, and compiles bounded,
auditable execution contracts that existing coding agents can consume.

`v0.1.0` is intended as the first public tag. It covers four of the product's five
stages:

```text
Diagnosis → Prescription → Compilation → Validation
```

Controlled Apply — the stage that would write to your project — is deliberately not in
this release.

## What you can do with it

```bash
pip install /path/to/agent-foundry     # not on PyPI yet; install from a clone
agent-foundry doctor
agent-foundry inspect  ./my-repo --format yaml
agent-foundry adopt    ./my-repo --format yaml
agent-foundry resolve-toolkit ./my-repo --format yaml
agent-foundry compile  ./my-repo --work-item work-item.yaml \
                       --role-id builder --run-id run-001 --render
agent-foundry validate execution-bundle.yaml --kind execution-bundle
```

Eight subcommands ship, and that is the whole list. `adopt` is preview-only: it prints
a plan and writes nothing. There is no `--apply`. Nothing in this release mutates a
target project.

Every command is thin dispatch over a Python API (`agent_foundry.inspect`, `.adopt`,
`.work`, `.toolkit`, `.compile`, `.render`, `.verify`); there is no behavior behind a
command a Python caller cannot reach.

Committed, regenerable examples of every output contract live in
[`examples/e2e-synthetic/`](../../examples/e2e-synthetic/).

## What it produces

Typed, versioned, serializable contracts: `ProjectIntake`, `ProjectManifest`,
`AdoptionChangeSet`, `WorkPlan` of causal Work Items, `ToolkitLock`, `TaskToolkit`,
`IntegrationSpec`/`SecretRef`, `ExecutionBundle`, `EvidenceBundle`, `ExecutionReceipt`,
and a concise agent-facing Markdown projection of the bundle.

Three properties are worth naming because they are what the release is for:

- **Least capability is enforced, not aspirational.** The Task Toolkit is a strict
  subset of the Project Toolkit, and every subtraction records the project fact that
  caused it.
- **Authority is bounded by what an owner declared.** Compiled write authority is the
  intersection of the Work Item scope, the role contract, and the project's declared
  write envelope. Undeclared grants nothing.
- **Raw secrets are referenced, never embedded.** Serialization and rendering fail hard
  on known vendor credential formats, in values and in mapping keys alike.

## What it does not do

**It does not execute anything.** V0.1 compiles and verifies contracts. The evidence in
an end-to-end run is what a runtime *would* report, and every receipt records that
substitution as a stated limitation. A coherent bundle is not completed work.

Also not in this release: broad Controlled Apply, autonomous agent dispatch, deployment
automation, an MCP server, live tracker/repository write adapters, and any large Skill
or provider catalog.

## Before you rely on it — read the limitations

The full, measured list is in the README under
[Known limitations](../../README.md#known-limitations). The three that will affect you
first:

1. **A project that has not declared itself cannot reach an `ExecutionBundle`.**
   Inference may tighten controls but never expand authority, so operating
   characteristics come from your `.foundry/project.yaml`. Across 12 real repositories,
   the median project populated 1 of 16 manifest dimensions and 11 of 12 resolved no
   roles at all. If you want output, declare first — adoption will tell you so.
2. **The embedded-secret guard is not exhaustive.** Only Tier A (known vendor formats)
   blocks, and it matches at a token boundary: a credential glued into a longer
   identifier with no separator, or joined by an underscore, is detected by neither
   tier. Tier B entropy is advisory, does not block, and fires on ordinary prose. A
   clean scan is not proof that no credential is present.
3. **Validation proves coherence, not correctness.** Containment proves a granted path
   lies inside its declared bounds; it cannot prove the bound was the right bound. A
   correct compilation of a wrong diagnosis passes every check — which is a real defect
   this project shipped and fixed, and the reason diagnosis quality is treated as a
   product concern rather than a validator concern.

Convention discovery is four hardcoded patterns and nothing above confidence 0.5. The
`BLOCK` adoption decision has emit sites but was triggered by none of the 12
repositories surveyed, so treat it as unverified against real input. Inspection can
conclude from a truncated read without saying that the read was truncated.

[`docs/foundry/v0.1-readiness-report.md`](../foundry/v0.1-readiness-report.md) is the
long form: what was proved by running the path, what could not be proved, and every
remaining gap with its classification.

## Compatibility

- Serialized contracts carry `schema_version: "0.1"`. A build accepts the same MAJOR
  and a MINOR no newer than its own, so a `0.1` build reads `0.0` and `0.1` and rejects
  `0.2` and `1.0`. Incompatibility fails explicitly; it is never coerced.
- `CapabilityRegistry` and `ToolkitLock` carry `foundry_compat: ">=0.1,<0.2"`, compared
  on MAJOR.MINOR.
- `0.1.z` will stay backward-compatible. `0.2.0` may change contracts and the capability
  boundary — pre-1.0 minor releases are allowed explicit breaking changes, and any
  migration will be explicit rather than implicit.
- Names not exported from the documented modules are private and may move.

Full policy: [`docs/foundry/09-release-and-versioning.md`](../foundry/09-release-and-versioning.md).

## Verification

Verified for this release from a fresh `git clone` and a non-editable install into a
clean virtual environment, with the CLI exercised from a working directory unrelated to
any checkout: 1434 tests pass under bare `pytest`; the end-to-end suite is 152 of them;
every artifact in `examples/e2e-synthetic/` regenerates byte-identically; and
`agent-foundry doctor` returns each of its three exit codes correctly.

Commands and captured output:
[`docs/foundry/v0.1-release-certification.md`](../foundry/v0.1-release-certification.md).

## What is next

The V0.2 boundary is meant to be decided by evidence from using V0.1, not precommitted.
The likely line is bounded Controlled Apply with rollback receipts, a first MCP facade,
and selected live adapters.
