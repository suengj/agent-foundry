## [0.1.0] - 2026-08-27

> **Prepared, not yet released.** This section is written for the `v0.1.0` tag and dated
> for the day it was prepared. **No `v0.1.0` tag and no GitHub release exist yet**; both
> require explicit authorization from the repository owner. If the tag is created on a

First public preview. Diagnosis -> Prescription -> Compilation -> Validation, read-only
and preview-only throughout: no command in this release writes to a target project, and
nothing executes the work an `ExecutionBundle` describes.

Read [Known limitations](README.md#known-limitations) before relying on any of it, and
[`docs/release-notes/v0.1.0.md`](docs/release-notes/v0.1.0.md) for the release notes.

Entries are grouped in the order the work landed, so a category heading may appear more
than once under this release.

### Added

- Inspection recognises nested projects and does not read their files as the target's evidence. A directory below the root carrying its own project manifest (`pyproject.toml`, `package.json`, `Cargo.toml`, `go.mod`, `setup.py`) or its own `.git` is a separate unit of ownership: its `Dockerfile` is not the target's deployment, its `env.example` is not the target's credential surface, and its build metadata is not the target's. Measured on Agent Foundry itself, where eight fixture repositories under `tests/fixtures/projects/` produced two wrong readiness findings, 22 of 25 adoption evidence references, and a `WRAP` Work Item whose compiled write scope was seven files nobody wanted changed — a correct compilation of a wrong diagnosis, which no validator can catch because a granted path being the *wrong* path is not something containment can see. Each boundary emits a `nested-project` observation, so the exclusion is a stated fact rather than an absence. The marker set is deliberately narrower than `PACKAGE_METADATA_FILES`: a lock file travels with a project, it does not constitute one.

- `agent_foundry.verify.validate_compiled_slice` runs every published validator over one compiled slice and returns a `SliceValidation` naming what ran and what could not. `accepted()` is False whenever an applicable validator did not run, because a verdict over a subset of the checks is not a verdict over the slice however many of that subset passed. The function raises if a validator in `verify.claims.VALIDATOR_IDS` is neither run nor recorded as skipped, so one added to the catalog cannot quietly reduce a verdict's coverage without changing its answer. It holds no rule of its own: every check is imported from `verify.validators` and `verify.explain`.
- `ProjectAuthority.write_scope` on `ProjectManifest`, read from `.foundry/project.yaml`. This is the outer envelope compiled write authority is intersected against, and it replaces a `write_scope=["src/", "tests/"]` default on the builtin `builder` role — a project-shape assumption living in core, which made every project whose changes land elsewhere compile to a bundle authorizing no change it could make. Undeclared grants nothing: an owner who has not said which paths agents may touch has not granted write authority.
- `SkillSpec.produces_evidence` names the typed evidence classes running a skill can produce. `outputs` names artifacts for a human reader; this is what a Work Item's `required_evidence` can be satisfied by, and it is what makes a skill needed rather than merely permitted.
- `agent-foundry validate <artifact> --kind <kind>` runs every published validator that applies to one contract artifact. AF7 shipped validation as a Python API only, so the stage was not reachable from the command line; the README advertised the command anyway. Exit codes separate what a caller has to tell apart: `0` every applicable validator ran and accepted, `1` examined and rejected, `2` the request could not be carried out, `3` everything that ran accepted but a validator that applies had no input. A skipped validator is named in `not_run` with the input it lacked, never omitted. The subcommand adds no rule of its own; `agent_foundry.verify.cli_api` is dispatch, and a test parses its AST to keep it that way.
- `AdoptionAction.WRAP` has a producer. It fires when a repository carries an integration or credential surface and no `IntegrationSpec` declares how an agent reaches it: the surface is retained and the access path moves behind a declared adapter with `SecretRef` coordinates, which is `docs/foundry/02` §7's own definition. The action had no emit site anywhere while the contract listed it as a brownfield category, so code and contract disagreed.
- `AdoptionGap.scope` carries the repository paths an adoption change touches. `target` names a logical surface ("test-harness"), which is not a path, so compiled write authority intersected it with the declared bounds and got nothing: an adoption Work Item compiled to repository-write authority over an empty write scope. Empty stays legal — a change to a file that does not exist yet has no path to name — and the bundle then grants no write.
- A brownfield project with no `.foundry/project.yaml` is told to declare one. `MIGRATE foundry-project-declaration` had only a greenfield emit site, so a retrofit plan for an undeclared repository reported a clean adoption while every toolkit, role and authority decision behind it read an unknown manifest and selected nothing.
- `tests/e2e/friction_survey.py` measures adoption friction across many repositories and emits counts only. Its record type holds integers, booleans, and terms from Foundry's own fixed vocabularies, so a path, project name, or file content has no field to reach; a test asserts that shape rather than trusting how the tool is used.
- `examples/e2e-synthetic/` holds generated `.foundry` artifacts, the rendered agent-facing contract, and the full slice-validation record for a synthetic fixture repository. Every file is regenerated and byte-compared by the test suite, so an example cannot document a shape the code no longer produces.
- `docs/foundry/v0.1-readiness-report.md` records what the V0.1 slice proved, what it did not, the measured friction for both targets, and every remaining gap classified against `docs/foundry/08`.

### Fixed

- The Task Toolkit is the minimum subset `docs/foundry/04` §4 specifies. Only a *permission* filter ran, so every skill sharing a work class with a Work Item was handed to it and the Task Toolkit was the Project Toolkit exactly — while the compiled bundle permitted 2 of 5 capabilities, meaning the narrowing happened one stage later and the contract's own stage did nothing. Selection is now need-based: a workflow that requires the skill, a project policy that requires it, or a typed evidence class the Work Item requires, plus a read baseline so an item can always look at its own scope. Every subtraction records the reason it was subtracted.
- `compile_work_item` refuses to return a repository-write bundle with no write path. Every structural check passed on such a bundle and an executor holding it could not change a single file, so `agent-foundry compile` reported success for work that cannot be done and only a separate `validate` call would have caught it. The error names the Work Item scope and the declared bounds it failed to intersect.
- `validate_write_scope_containment` checks a granted path against every declared write bound, names which one it fell outside, and reports MISSING when no authority declared any bound at all. It previously checked the role's scope alone, so a project-declared envelope could not be verified and an unchecked grant read as a verified one.
- `verify.explain.AUTHORITY_AXES` names the classification dimensions the inspector actually emits. Each axis was paired with a human label (`"External effect"`, `"Autonomy"`) that matched no finding, so the declared baseline was always empty and `assess_inferred_fact_tightening` reported **every correctly-declared project as widened by inference**. Unreachable until a declaration could populate those axes, and exposed by the first one that did.
- An owner-declared `.foundry/project.yaml` is read in full. Inspection parsed one key out of it (`intake_mode`) and reported every other dimension as "not observable from repository inventory alone" — including `project.name`, which was in the file — while adoption emitted `KEEP foundry-project-declaration / "Existing declaration is authoritative and compatible"` in the same run. `ProjectManifest` synthesis also hardcoded `name`, `temporal_mode`, `reversibility`, `consequence`, `ambiguity`, `concurrency` and `assurance.required` to empty regardless of input. The measured consequence: a manifest carrying 1 of 16 dimensions, a Project Toolkit with zero capabilities, skills and roles, and `CompileError` for every role — the path from a repository to an ExecutionBundle could not be completed at all. Inference is unchanged and still supplies only `intake_mode`: what is promoted is what an authority declared.
- Adoption work can be built, tested and reviewed. `WorkClass.ADOPTION` was absent from the `bounded-change`, `deterministic-test` and `independent-review` skill triggers, so the only work class the adoption planner emits could select no skill except read-only inspection — and the planner marks its own `HARDEN`/`CONSOLIDATE`/`MIGRATE` changes `bounded-policy` precisely because applying them writes repository files.
- A Task Toolkit no longer pins a workflow it cannot staff. When no preferred workflow was available the resolver fell back to `sorted(available)[0]`, selecting a workflow the preference order had rejected and whose required skills the work item may not carry; `toolkit-coherence` validation then rejected the compiled result. No suitable workflow now resolves to no workflow, with the exclusion recorded.
- An adoption Work Item's `required_evidence` names typed evidence classes. It was the prose `"implementation diff"` and `"validation output"`, which no `EvidenceClass` names, and an unrecognised requirement resolves to MISSING rather than passing unexamined — so every adoption item's evidence was permanently unsatisfiable.
- Forbidden scopes are computed by containment, not string equality. A role bound of `tests/` narrowed to a grant of `tests/conftest.py` was emitted as forbidden while the file inside it was granted, and `write-scope-containment` correctly rejected the contradiction. A partially granted bound is no longer listed: the positive `write_scope` is the grant, and there is no path expression for "`tests/` except one file".
- A virtual environment is skipped by its `pyvenv.cfg` marker rather than by directory name. `SKIP_DIR_NAMES` matched `.venv` and `venv`, so a `.venv-lane` (or `env`, or any local convention) was walked: it sorts before every source directory and holds thousands of files, so it consumed the entire 2000-entry traversal budget and inspection reported "No test entrypoints observed" about a repository with a full test suite, changing 4 readiness dimensions and 2 adoption changes.
- Validation rejects a bundle that is internally consistent and operationally empty. `execution-bundle-completeness` now reports a repository-write bundle that grants no write path. The validator's claim is updated in both directions — it proves a write path exists, and it states that it cannot prove the path is the right one.
- The rendered contract says how much it left out. The selection-provenance summary stopped after ten records silently, so a truncated list read as the complete one; the forbidden-scope list grew with the project's declared envelope rather than with the work. Both now name the count they stopped at, and the forbidden-scope note restates that only the write scope is granted.
- An autonomy-deferral adoption change cites the source it is evidenced by. It carried evidence refs with no `source_ref`, unreachable until a declared `execution.autonomy` made the change emittable.

### Changed

- `tests/fixtures/valid/work_item_contract.yaml` scopes work to repository paths rather than prose. `scope` bounds compiled write authority, so an item scoped to "models package" can be granted no write at all.
- The README's end-user flow separates the eight commands that ship from the five that do not. It previously listed ten as "approximately" the intended experience, of which `profile`, `work plan`, `render`, `reconcile` and `validate` had no subcommand at all; `validate` is now real and the other four are marked as not built.
- `docs/foundry/08` §4.1 records that §4.2's conservative authority rule governs profile synthesis. Read alone, §4.1 suggests synthesis derives profile values from observation; an implementer following it builds a system that grants authority by inference. The measured cost of the correct reading is stated there.

### Fixed

- An aliased workflow step no longer produces a second finding evidenced by a different step. A YAML alias resolves to the anchored node with its source marks, so `- *checkout` was the same object as the step it copies and was emitted again carrying that step's source line — a line which does not support it. A step is accepted once, where it is actually written inside its own `steps` sequence.
- `test-invocation` recognises a quoted command name: a shell runs `"pytest" -q` exactly as it runs `pytest -q`. Quoting still distinguishes data everywhere else, so `sh -c "pytest -q"` remains an invocation of `sh`.
- Effective-behaviour conventions are detected and evidenced in one pass, so the two can no longer disagree. Detection previously decided a claim from structure and a second pass re-scanned raw lines for the value it had found; that seam produced a false claim (an `actions/checkout` reached through a YAML alias was evidenced by the anchor declaration, which configures nothing) and a false negative (a folded `uses: >` scalar was accepted by the detector and then silently dropped because its value spans lines). Detection now returns the source text it matched on. Where evidence cannot be produced the claim is not made at all rather than made falsely.
- `test-invocation` decides whether the `test` recipe *invokes* pytest by shell command position rather than by substring. `echo "# pytest -q"` and `echo word#pytest` name pytest as data, not as a command, and no longer produce a convention; `pytest -q`, `python -m pytest`, `PYTHONPATH=src pytest`, `uv run pytest` and `.venv/bin/pytest` still do. A line that does not parse cleanly (an unterminated quote) establishes nothing.
- Comment text no longer supports a convention that claims effective behaviour. `test-invocation` searched every line of the Makefile `test` recipe for "pytest" and `ci-checkout` searched every workflow line for `actions/checkout`, so a commented-out recipe line or a commented-out `uses:` step produced a positive convention asserting an invocation or a checkout that does not happen. Recipe lines are now read as the shell would read them (make's `@`/`-`/`+` prefixes consumed, trailing comments stripped, `#` inside a quoted string left alone), and `ci-checkout` rests on a checkout step parsed out of `jobs.*.steps[*].uses` rather than on any line mentioning the action. The `test-runner` and `git-policy` conventions are unchanged by design: they claim a textual mention, which commented text genuinely is.
- Inspection evidence is the text that produced the claim. The `git-policy` convention matched `commit ... not` but quoted the first line containing "commit", so an `AGENTS.md` reading "Always commit early and often." / "Do not commit secrets to the repo." was cited by its opposite; every constraining line is now quoted as its own convention. `test-invocation` claimed pytest appeared "near a test target" while only checking that pytest and a `test` target both existed somewhere in the Makefile; the claim is now backed by the `test` target's own recipe lines. `test-invocation` and `ci-checkout` quote the matched source line instead of a generic description.
- Unobservable paths are reported instead of silently disappearing. A directory the OS refused to list was counted as a skip and nothing else, and a file that could not be read came back indistinguishable from an empty one — so "not allowed to look" read downstream as "nothing there". Every unreadable path now emits a `path-unobservable` observation naming it.
- Inferred `intake_mode` confidence reflects signal strength rather than evidence presence. A repository containing only `.github/workflows/c.yml` scored `brownfield | inferred | 0.7` because at least one evidence ref existed; it now scores 0.5, and confidence rises only as independent signals accumulate. Inferred findings state which signals they rest on in the previously unused `reason` field.
- The read-only regression harness compares mtime. `_tree_snapshot` covered content and directory `st_mode` but not mtime, so an inspector that touched every file it read passed the test that exists to prevent exactly that; verified by making the inspector perform an mtime-only mutation and confirming the named read-only tests now fail.

### Added

- `TraversalStats` reports why entries were skipped: `entries_skipped_ignored_dir` (deliberate cache/vendor skips), `entries_skipped_refused` (containment and symlink refusals), and `entries_skipped_unreadable` (OS refusals), plus `entries_unobservable`. `entries_skipped` is unchanged and remains the total, so existing consumers keep working.

### Changed

- `DecompositionQualityFlag.MEGA_ITEM` (`mega-item`) is now `CROSS_OUTCOME_IDENTITY_COLLISION` (`cross-outcome-identity-collision`). The engine splits these units into separate work items and sets `work_item_id=None` on the issue; no mega item is ever produced, so the old name described an outcome that does not occur. `agent_foundry.models.__all__` is unchanged — only the member of an exported enum was renamed.
- Decomposition quality issues relate ids that resolve inside the plan. `cross-outcome-identity-collision` related outcome ids and `mixed-work-class` related work-class *names*, so neither diagnostic pointed at anything a reader could open. Both now relate the capability unit ids that disagreed; the outcome ids and class names moved into the message, where they explain the finding.
- `agent-foundry doctor` separates a package self-check from a target-project check. The project check resolves artifacts by discovering a project root upward from the working directory (or from an explicit `agent-foundry doctor PROJECT_PATH`), never from the installed package's own location. Exit codes distinguish the two: `1` when the installation itself is broken, `2` when a named project is missing expected artifacts, `0` when no project is in scope.

### Fixed

- Work decomposition fails clearly instead of crashing when `WorkClass` grows. `_WORK_CLASS_PRECEDENCE` ranks every member by hand, and a member added without extending it raised a bare `KeyError` from inside the rank lookup — only once two unlike capability units happened to merge. The merge now raises `WorkDecompositionError` naming the unranked member and the tuple to extend, and a named test fails in CI before any input reaches it.
- A cycle in a large dependency graph is still reported as a cycle. Cycle *detection* is iterative and handles thousands of nodes, but path reconstruction recursed once per node and raised `RecursionError` at 3000 — on the already-failing path, so an actionable "circular dependency: a -> b -> a" turned into a stack overflow. Reconstruction is iterative; node visit order and the reported path are unchanged.
- The Work Item contract can no longer be widened in place. `frozen=True` stops rebinding an attribute but leaves a `list` field open to `.append()`, so `context.contract.scope.append(...)` silently changed the serialized contract that bounds compiled write authority. Sequence fields on the work model are tuples.
- `attach_execution_run` no longer accepts a run id twice, and runs keep attach order. Attaching `run-000` to a 50-run context produced 51 runs, and sorting by id ordered them lexically, so `run-9` preceded `run-049` and the run sequence read as a history that never happened.
- `runtime_external_validation_requirement` says something about the item it is on. It was one hardcoded sentence stamped onto every Work Item, including READ_ONLY discovery-only ones with nothing external to validate. It is now derived from the item's authority class and required evidence, and is unset for items with no external effect.
- A toolkit capability excluded from a Task Toolkit now cites the fact that caused the exclusion. The sibling role exclusion in the same function already cited the work class; the capability exclusion recorded a rationale but no `project_fact` or `policy_id`, so an exclusion could not be attributed to anything. Found by the new decision-explainability validator.
- Adoption authority guard is enforceable. `assert_change_set_respects_authority` previously compared `change.target` against two literal strings, one of which (`impact.external-effect`) had no emit site and was spelled with a hyphen where the classifier uses `impact.external_effect`; the guard could not raise for any planner output. Authority-bearing targets are now recognised by the manifest field they move, under either spelling, and an unclassified target fails closed instead of passing unexamined.
- Unknown current authority no longer reads as "not widening". `widens_autonomy` and `widens_external_effect` returned `False` whenever the current level was unknown — the ordinary case, since AF2 leaves manifest fields unknown by design. Unknown now ranks below every declared level, so a proposal against an unknown baseline is treated as widening.
- `test-harness` HARDEN is labelled for what it does. Adding or strengthening test entrypoints writes repository files, so both the greenfield and brownfield changes are `bounded-policy` / `proposed` rather than `none` / `auto-applicable`, matching their file-creating siblings.
- Adoption change evidence stops fabricating and discarding provenance: `source_ref` is the file the evidence came from (or `null` when none was located) instead of a hardcoded `"."`, every `agent-rule-fragmentation` finding produces a change rather than only the first, and the brownfield `test-harness` and `execution.autonomy` changes cite the entrypoints they rest on.

### Removed

- The unreachable second copy of the undeclared-outcome check inside `_packages_for_outcomes`; the identical check in `decompose_work` already ran on every path. The dead `work_class.value` tiebreak in `resolve_merged_work_class` is gone too — precedence ranks are unique per member, so it could never be reached. The `unpackaged` post-condition and `_assert_unique_work_item_ids` stay, now with comments saying why they are deliberate defense-in-depth rather than live checks.

### Added

- Reciprocal exhaustiveness guards for the work model's enum-keyed lookup tables (`tests/test_work_vocabulary_exhaustiveness.py`), following the existing docs-vocabulary guard. Each way a table can drift from its enum gets its own named failure naming the offender and the table: a member the table does not rank, an entry that is not a member of the enum at all, a member listed twice, and — since `WorkClass` is a `StrEnum`, where a bare string entry can collide with a real member's key — any entry lost building the rank dict. Completeness in one direction is not evidence of a correct table: an extra or duplicated entry leaves a one-way `enum - table` check passing.
- Validation, evidence, reconciliation, and learning Core API (`agent_foundry.verify`). Fourteen validators over finished artifacts — contract schema compatibility, work dependency graph, Project/Task Toolkit coherence, authority ceiling, write-scope containment, role separation, integration preflight, required evidence classes, evidence-bundle completeness, provenance completeness, `ExecutionBundle` completeness, lifecycle separation, receipt completeness, and decision explainability.
- Validators are derived independently of the code that produces the artifacts they check. `agent_foundry.verify.independent` re-derives external-effect ordering, repository-path resolution, integration-health ordering, version parsing, finding-disposition obligations, and the evidence-state partition from the durable contracts. Pydantic model validators count as producers — they decide whether an artifact may exist — so their helpers are off limits to the validation layer, and the obligations they encode are restated from docs/foundry/06 §9 and §4 rather than reused.
- Unknown never reads as safe, on either side of a sibling pair. `evidence_state_partition_conflicts` validated the attained list against the evidence progression but not the not-required list, so `not_required_evidence_states: ["SOMEDAY"]` passed lifecycle validation — "absence is never PASS" broken inside the module written to enforce it, and the fifth time this project has shipped that defect. Both lists are now checked through one shared helper, and an unrecognised value is BLOCKED rather than MISSING: an exemption is a positive claim that an obligation does not apply, so a value naming no evidence state is not an incomplete record but a wrong one.
- Vocabulary membership is validated before any membership test, rank lookup, or dereference, uniformly across `verify/`. Three lifecycle fields on a receipt accepted an unrecognised value and returned PASS; the integration-health ladder and the external-effect rank raised `ValueError`/`AttributeError` on one. An exception is not a fail-closed verdict — it returns no report, so nothing is recorded about why the artifact was rejected and the caller is aborted. Every validator now scans its inputs first and returns BLOCKED for any enum position holding a value from no vocabulary, and the ranks and ladders are total so a caller that skips the scan still cannot crash.
- Caller-supplied sequences are read exactly once, and a bare string is not a sequence. Adding parameter vocabulary checking introduced the classic double-consumption bug: the guard iterated the caller's iterable to check it, then handed the same exhausted iterator to the real logic. Eight parameters were affected, and the symptoms varied enough that none looked like one bug — a valid generator was BLOCKED on one, raised `TypeError` on another, and on three more produced a *clean pass over nothing*: "0 work item(s) form an acyclic graph", a vanished review-independence finding, and a MISSING that read like a legitimate verdict. Every entry point now materializes each sequence parameter at its door and uses that copy everywhere; a `str` is reported as a shape violation rather than read one character at a time; and a non-iterable produces a finding instead of an exception.
- Producers that have no report to return fail loudly rather than treating a malformed argument as empty. `build_decision_trace` and `assess_inferred_fact_tightening` raise; `classify_repeated_failures` returns `unknown` with the reason, because its return type can express that. Treating a bad shape as an empty sequence is the worse answer for the tightening check in particular — "no declared baseline" is exactly what makes an inference look like authority widening.
- Vocabulary is validated at both entry points, not just one. The policy had been applied to values *carried on the artifact* and not to values *arriving as arguments*, so `validate_lifecycle_separation(receipt, required_evidence_states=["SOMEDAY"])` raised `AttributeError` instead of returning a verdict. A shared gate now covers enum-typed parameters alongside artifact fields, and the same sweep found three model arguments that never reached any gate — `registry` on two validators and the `artifacts` mapping on receipt completeness, all read but none obviously "examined". Two loosely typed parameters that accepted a non-model and raised on it now return BLOCKED as well: `Iterable[tuple[str, Any]]` and a bare model annotation both admit objects that are not contracts.
- The vocabulary gate moved into `verify/independent.py` so validators, explainability, and reconciliation all reach the same one. Explainability had grown its own copy inline, which is how a rule becomes something each new entry point has to remember separately.
- The round-2 claim to have audited every vocabulary and ladder check in `verify/` did not hold: a manual sweep found the list asymmetries and missed the three lifecycle fields and the health ladder. The claim is replaced by a mechanical one. A standing test enumerates every enum-typed position — nested models and lists included — on every model argument of every validator, forges each with an off-vocabulary value, and requires that the validator neither raises nor accepts. The enumeration is derived from field annotations, so a field added to a contract tomorrow is swept the day it is added. Running it found 15 defects where a manual pass had found 4, and two more that a top-level-only sweep would have missed. A companion sweep reads each public entry point's signature, so an enum-typed parameter must be swept or carry a recorded reason, and every model argument must appear in its validator's gate — checked against the gate text, not the signature, since an earlier version of that test found the parameter in its own annotation and would have passed with the gate empty.
- The same audit fixed six further instances of the class rather than only the reported one: evidence-bundle completeness now checks the vocabulary of item classes *and* declared exemptions; required-evidence checks the exemption side as well as the requirement side, and reads the serialized payload so a forged bundle is rejected instead of raising `AttributeError`; an unusable `forbidden_scopes` entry is rejected like an unusable granted path, because a bound that resolves to nothing denies nothing; a forbidden capability outside the task toolkit is rejected like an allowed one; registry membership is checked for the project lock as well as the task subset; and reconciliation reports an unrecognised tracker evidence declaration instead of crashing on it. A registry of sibling pairs is now a test, so adding a pair half-checked fails.
- The dependency guard covers every module in `verify/`, not just the primitives. It reads each module's import graph for the five producing packages, and it *discovers* producer-owned validation rules by walking `models/` for functions called inside a `@model_validator` or `@field_validator` body — so a producer rule written tomorrow is protected the day it is written, without a hand-maintained list. Tests prove the guard catches both `from ... import rule` and `module.rule(...)` spellings.
- Producer-owned validation rules sit behind an import boundary. The two rules a validator could be tempted to reuse moved to a private module of their own, imported only from inside the model-validator bodies that need them, so importing the DTOs no longer puts those functions — or their module — into any namespace a verifier can walk to. No module under `verify/` may name that module by import, attribute, or string literal. This is what closes *pre-capture*: a reference bound at import time, before anything could patch it, which neither a rule-name scan nor a runtime tripwire can see.
- The claim that the tripwire caught a producer rule "by any route" was false and has been removed. `monkeypatch.setattr` rebinds a module dictionary entry; it cannot rewrite a reference captured before it installs, and a module-level capture, closure, default argument, or `functools.partial` all keep the original callable. `claims.py` now states what the three guards together do prove, and records the residue — a dynamically assembled module path, or a future third module that legitimately imports a rule — plus the complete answer (a process boundary) as an explicit V0.1 limitation rather than a promise.
- A behavioral guard backs the syntactic one. The AST scan reads source, so a call assembled at runtime — `getattr(__import__("agent_foundry.models.interaction", fromlist=[...]), "evidence_state_partition_violations")(...)` — was invisible to it and could restore the exact producer coupling just repaired. Enumerating dynamic spellings would be a losing arms race, so every producer rule is now wrapped in a tripwire and the whole validation surface is run against it: any call originating in validation logic fails a named test, by any route. Legitimate use is distinguished from coupling by which boundary the call stack crosses first — a pydantic frame means a model is being constructed, a `verify/` frame means validation logic asked directly — so the guard does not fire when verify builds its own result models. The AST guard stays for cheap feedback on static regressions; two guards by different mechanisms is the same principle as the rest of this Work Item.
- Every validator has a mutation test that follows one order: neutralize the producing function, show a *real production path* emitting or accepting the defective artifact, then show the validator rejecting it. Producer acceptance is demonstrated by `compile_work_item` returning a bundle that grants write access above the repository root, `build_execution_receipt` stamping a digest that matches no artifact, and `model_validate`/`load_yaml` ingesting payloads their own rules would normally refuse. Where a validator has no code producer — evidence bundles arrive from outside Foundry — the production path is model ingestion, and the test names it as such.
- `agent_foundry.verify.claims` publishes, per validator, what it proves and what it cannot. The one check that is not an independent derivation (receipt digest comparison) says so and states what it is worth: recomputation runs through a call site deliberately separate from the one that stamps a receipt, so neutralizing the stamp is caught, but both wrap the same serializer. Tests keep the catalog and the code in one-to-one correspondence, and tie every `independently_derived=True` to the dependency guard rather than to an assertion.
- Absence never resolves to a passing state. An unobserved integration, an evidence class with no typed passing item, an unrecognised evidence requirement, an unspecified `required_evidence` list, a report with no findings, and a runtime that was never read back all resolve to `MISSING`. `NOT_REQUIRED` is returned only where a requirement was declared absent.
- Typed primitives grown to carry what verification needs: `EvidenceBundle` gains revision identity, typed evidence classes and results, declared not-required classes, and unresolved findings; `ReviewDecision` records the implementing role it is independent of and refuses to name it as its own reviewer; `ExecutionReceipt` records exact work/run/role/revision/toolkit/permission/budget identities with content digests, adapter versions, budget consumption, cleanup state, next action, known limitations, and dispositioned findings.
- `RunFinding` enforces the obligation each disposition owes: a BLOCKER cites evidence, a RESIDUAL names follow-up work, a HYPOTHESIS states a falsifiable prediction and the evidence condition that would settle it, and a HUMAN_REQUIRED finding gives an escalation reason.
- The three lifecycles stay three lifecycles. Work lifecycle, execution state, and evidence state are separate fields with pairwise-disjoint vocabularies; `ExecutionReceipt` records attained and not-required evidence states as lists, and a receipt that carries only the single-state projection is reported incomplete. Named tests fail if the three are conflated.
- Read-only reconciliation across tracker, repository, and runtime authorities (`reconcile_work_item`). It expresses `NOT_REQUIRED`, `MISSING`, `PASS`, `BLOCKED`, and `HUMAN_REQUIRED` per dimension without inventing facts, and proposes state updates rather than applying them: a `StateProposal` against any authority other than Foundry itself cannot be constructed as auto-appliable. A test runs the default path inside a sandbox where every write, subprocess, and socket call raises, and a second test proves that sandbox bites.
- Reconciliation fixture tests over genuinely divergent states: a tracker reporting done against a repository with no integrated revision; a complete repository against a runtime still serving an older revision; an unobserved runtime; a rejected review; failing test evidence; and an evidence bundle claiming a revision the repository does not report.
- Decision explainability as structured audit evidence rather than narration: which facts and policies caused each role, skill, integration, capability, workflow, and permission-profile decision; provenance and confidence for material inferred facts; and whether inferred facts only tightened controls. An inference that raises the authority a declared-only baseline supports escalates to `HUMAN_REQUIRED`, and — following the AF3 rule — an unknown baseline ranks below every declared level, so silence is never read as permission.
- Repeated-failure classification into contract, context, permission, tool, and harness categories. Classification reads structured signal fields only; a free-text failure message is never classified, and a signal that supports no category, or two equally, returns `unknown` with the candidates recorded. Two failures in one class shift suspicion to the harness or the work contract rather than triggering further retries.
- End-to-end adoption property tests over a planner-input corpus: no planned change is both authority-widening and `auto-applicable`/`none`; no change whose action requires writing repository files (MIGRATE/HARDEN/CONSOLIDATE/WRAP) is `auto-applicable`/`none`; and every planned target is classified by the authority guard, so a new `_change(...)` call site cannot silently escape review.
- The adoption property tests assert their own coverage. Every on-disk fixture emits zero authority-widening changes, so a property that only inspects widening changes passes however they are labelled; the corpus now includes an input that reaches the planner's authority-proposal path, and a named guard test fails if the corpus ever stops producing one.
- The adopt determinism test now compares output across PYTHONHASHSEED and working directory instead of running both subprocesses with the same environment and comparing a run to itself.

- Work Item compiler (`agent_foundry.compile`) producing minimum Task Toolkit, role-specific `ExecutionBundle`, and provenance-bearing selections with authority intersection.
- Concise Markdown renderer (`agent_foundry.render`) projecting agent-facing contracts from `ExecutionBundle` only.
- `agent-foundry compile` CLI subcommand with `--render` for Markdown projection.
- Compiled write scope is a true path intersection of Work Item scope and Role Contract scope: `.`, `./`, redundant separators, and `..` traversal are resolved before comparison, and any bound that resolves to the repository root, an absolute path, or above the root grants nothing.
- Drive-rooted and UNC paths (`C:\repo\src`, `\\host\share`) are rejected as write-scope bounds rather than compared textually as if repository-relative.
- `validate_execution_bundle_authority` performs structural checks that do not call the compiler, so a forged or over-broad bundle is still rejected when compilation itself is wrong; an empty Role Contract write scope authorizes no write path rather than skipping the containment check.
- Selection provenance names the Work Item field that actually supplied the matching token (scope, objective, or title) instead of always claiming scope overlap.
- Work Item escalation conditions carried into an `ExecutionBundle` now have provenance, as stop conditions already did.
- `ExecutionBundle` provenance is bounded: every selected component and the highest-scoring near-misses are itemized, and the remaining candidates are accounted for by count rather than enumerated, so bundle size no longer grows with project material.

### Fixed

- Integration preflight health now gates Task Toolkit resolution instead of only being reported next to it. `docs/foundry/04` §4 promised the Task Toolkit subtracts unavailable integrations, but the task stage hard-filtered to the literal id `repository`, so an integration whose health was `unavailable` could still be pinned and handed to a run. An integration now reaches the Task Toolkit only when a spec declares it, observed health meets that spec's `health.required`, and its capabilities stay within the Work Item's authority ceiling; every subtraction carries a rationale.
- An integration id with no declared `IntegrationSpec` is no longer retained by the external-effect ceiling reconciliation. Requesting `work-tracker` on a read-only project without a spec resolved to `integrations: ['work-tracker']` while supplying the spec correctly resolved to `[]` — missing data widened the result. Unknown capabilities are now treated as the fail-closed maximum at both the project and task stages, and the lock ceiling chokepoint rejects a pinned integration it cannot check.
- Absent integration health evidence no longer reads as a health observation. `preflight_integrations` derived `configured` from `IntegrationSpec.auth is None`, inferring a lifecycle state from the shape of a declaration rather than from anything measured — so an integration that was never checked cleared a `required: configured` bar and reached the Task Toolkit. An unobserved integration is now `desired` whether or not it declares `auth`; the auth shape only changes the diagnostic message. Waiving verification is now a declaration (`health: {required: desired}`) rather than an inference drawn from missing data.
- Validator ids are presence-checked against the registry before being pinned. A registry with `validators: []` previously still produced a lock naming `evidence-contract` and `schema-compat`, neither of which could run.
- `work.read` is classified `read-only` rather than `shared-service-write`. Reading a work tracker changes no state, exactly as `runtime.verify` reads a runtime without mutating it; the old value denied trackers to read-only work items for no reason. `CapabilitySpec.min_external_effect` now documents the axis it measures so the classification is not re-guessed.

### Changed

- `ToolkitLock` pins `validator_versions` alongside `skill_versions`, `workflow_versions`, and `integration_adapter_versions`.
- **Behavior change:** resolving a toolkit without supplying `integrations` no longer pins the default `repository` integration, because nothing declares its capabilities or health. Declare an `IntegrationSpec` for every integration a project should be allowed to use.
- Task toolkit resolution derives `role_ids` from selected skills, filters workflow roles by work-item authority, and records explaining decisions when a work item cannot be satisfied from the project lock.
- Builtin registry skill triggers now cover `INCIDENT` and `CONTRACT_AMENDMENT` via honest extensions to existing skills.
- Write-scope intersection now truly narrows role and work-item bounds; read-only compiles clear advertised write scope.
- Markdown render path applies the embedded-secret guard; compile provenance records bundle fields and integration health.

- Toolkit resolution reconciles capabilities against the manifest-declared external-effect ceiling (not the selected profile), pins that declaration in locks, and raises on unsatisfiable hard policy requirements.
- Pre-release vocabulary correction: removed `external-shared` from `Statefulness` (use `persistent-shared-external`); removed `deterministic` from `AssuranceMode` (use `deterministic-tests`).
